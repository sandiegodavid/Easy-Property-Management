For a newly approved identity with verified recovery, the UI offers both Complete onboarding and Enable access. The backend accepts the same proof for either action without requiring an existing completion for Enable. Choosing Enable activates the owning access store, but completed() ignores that action, so no onboarding_completion is recorded. The design requires initial explicit completion and requires current recovery/completion evidence for ordinary Enable access.

Resolution: activation now requires a current-handoff completion for Enable. The UI offers Complete onboarding until that completion exists, then Enable for a disabled completed binding. Direct-command regressions cover initial rejection, renewed-binding rejection, successful completion/re-enable and original receipt replay after proof expiry or verifier change. Browser coverage checks both choices and stale-evidence gating.

SPECIFICATION — Recovery evidence

Status: resolved — 2026-10-31
File: /Users/dcai/Desktop/My Apps/Easy-Property-Management/application/apps/server/app/modules/hosted_admin/infrastructure/onboarding.py:180-204

activation() obtains the report entirely from its retained SQLite projection. It does not revalidate the protected artifact or compare the report's verifier identity with the currently pinned verifier. Replacing recovery tooling and updating verifier.json therefore leaves a pending activation able to use the superseded verifier's report until ordinary age expiry. The design requires a fresh restore drill after recovery-tool/format changes; the existing VerifiedReports.report() boundary correctly rejects this old artifact, but activation bypasses that check.

Require current verifier identity/provenance before issuing a new activation proof and expose superseded evidence as requiring verification. Preserve historical reports and the existing original-receipt reconciliation path for actions that already committed. Add a regression that changes the protected verifier pin between registration and first activation.

Validation: Registered a real signed report, replaced verifier.json with a different digest, and confirmed that VerifiedReports.report(id) rejected it with admin_verifier_signature_invalid while OnboardingRecovery.activation() still returned a new proof for that same report.

Resolution: checklist refresh reopens the protected report through VerifiedReports.report(), revalidating its signature/current verifier pin and comparing it with the retained projection. Missing, superseded or changed artifacts produce stale evidence and cannot issue a new activation proof. Tests preserve historical reports, require fresh verification under the new pin, and reconcile committed source receipts even after a control crash and verifier change.
