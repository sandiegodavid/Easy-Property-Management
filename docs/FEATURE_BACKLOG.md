## How to use this backlog

For current implementation, start with [module guides](README.md#current-modules). Feature links point to remaining acceptance or the current guide; historical design sources are in [the archive](archive/README.md).

Each item has a stable identifier, phase, delivery sequence, outcome, and ordered dependencies. New ideas should be added here before being surfaced in the product.

The sequence column gives the recommended delivery order. Optional sub-sequences such as 26a are stable insertion labels; execute only after all listed prerequisites, not at their table position. The dependency column contains only hard prerequisites and lists them from left to right in the preferred implementation order; it does not imply that each prerequisite depends on the one before it. `None` marks a true starting point.

UI-001 core browser delivery and acceptance are complete as recorded October 12, 2026. Current backend/UI behavior is documented in [the developer index](README.md), with [browser validation evidence](ui/validation.md). DASH-001 Home delivery completed October 14, 2026. DATA-002/003 and INGEST-002 own their operator workflows. ASST-001 owns shared assistant setup and health, with transport/source-specific UI in the corresponding features. LEGAL-001 and HOA-001 own their deferred interfaces. The ordered dependencies below govern delivery.

Features with required operator workflows can have verified backend/API scope while remaining in progress. `UI-001` delivers the core [operator design](ui/operator-experience.md). Each functional item includes its required operator UI and browser acceptance. LEGAL-001 and HOA-001 remain post-MVP. `AI-DRAFT-001` can provide a contextual draft on an existing issue without a connected assistant. ASST-001 delivers shared connection setup; each transport includes its qualification UI. Design approval does not mark implementation complete; later feature slices add capabilities only after their sources exist.

Superseded rows preserve historical sequence IDs and are not active implementation dependencies. The independent delivery paths are: AI-GOV-001 → AI-DRAFT-001 for a governed, operator-triggered draft; AI-GOV-001 → ASST-001 → one qualified transport (MCP-001 or ASST-FILE-001) for connected assistance; and AI-GOV-001/INGEST-001 → INGEST-002 → ASST-INTAKE-001 for assistant-discovered message review. The first connected draft additionally requires AI-DRAFT-001's registered action. ASST-001 shared-service/UI acceptance uses non-production fixtures and does not wait on its dependent transports; a real connection remains unavailable until its transport and action qualify. ASST-001's new technical recommendations are proposed, not accepted decisions. ASST-INTAKE-001 additionally requires the shared assistant boundary and one qualified transport, but neither MCP nor file exchange is mandatory for the other. All pending INGEST-001 review deficiencies remain readiness blockers before INGEST-002 starts. ISSUE-AI-001/002 are superseded: assistant source discovery and proposal suggestions belong to ASST-INTAKE-001, while INGEST-002 provides manual context/issue selection and presents Intake duplicate hints without requiring model matching. Production model adapters are capability-gated; AI-LOCAL-001 remains an optional pilot. Manual entry and review remain usable without a connected assistant. INGEST-002 owns its feature-specific approval/handler integration, Intake/Maintenance consequences and OPS recovery registration (former UI-001 Slice 40); ASST-001 owns shared assistant setup and health. No unsupported issue-review or assistant action is surfaced as available.

The status column shows delivery progress. `✅ Done` means the item is implemented and verified; `🟡 In progress` means implementation is underway but acceptance criteria remain; a blank status means it has not yet been completed. Completed dependencies appear as green badges in the dependency column. `⏭️ Superseded by X` retains a retired feature's historical sequence ID while pointing to its replacement path; that path is not proof that any assistant is qualified today.

The MVP is a single-user application that runs locally. It has no application authentication, cloud account, remote portal, or shared workspace. The product owner runs setup scripts for each MVP user; self-service installation and update flows are out of scope. Read-only Google Sheets authorization is used only to acquire a selected snapshot during a new workspace's onboarding import; it does not create an application user or an ongoing connection. Inbound messages may arrive through a separately authorized, qualified assistant under ASST-INTAKE-001 or by manual import; EPM holds no mail or SMS-provider credentials. A model call is not a mailbox connection. Standalone voice-note recording, transcription, and voice-based issue proposals are later local product extensions, not MVP prerequisites; they do not require an external account.
