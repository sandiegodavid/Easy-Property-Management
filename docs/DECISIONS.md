# Product Decisions

| Decision | Status | Rationale |
| --- | --- | --- |
| Serve independent landlords and property managers with approximately 1–50 rentable spaces. | Agreed | Keeps workflows practical and avoids enterprise-first complexity. |
| Run the MVP locally for one operator without authentication. | Agreed | The initial product should validate the core property-management workflows without SaaS account, hosting, or collaboration complexity. |
| Store MVP records and attachments locally with backup/export and restore. | Agreed | Local operation needs a clear durability and recovery path. |
| Keep each user's configurable workspace outside the Git-maintained application checkout. | Agreed | Code, migrations, templates, and setup tools belong in Git; real records, SQLite files, attachments, backups, and exports must not. |
| Use a Git-ignored local workspace locator at `application/config.local.json` and a versioned non-secret workspace manifest. | Agreed | The locator identifies the selected external folder without committing user data; the manifest gives the portable workspace a stable identity and format version. |
| Reference attachments relative to the workspace and move workspaces through a copy-and-verify workflow. | Agreed | Relative references support relocation, restore, export, and future SaaS migration without broken absolute paths or incomplete moves. |
| Use SQLite-consistent backups for a live workspace and keep connection credentials in the OS credential store. | Agreed | Copying only an open SQLite database file can be incomplete; external-account tokens are device-sensitive secrets and do not belong in backups or exports. |
| Require passphrase-based authenticated encryption for portable LOCAL-002 backup and export archives. | Agreed | Backups will contain sensitive leases, financial records, and future applicant evidence; a portable archive must remain recoverable on another machine without storing its passphrase in the workspace, Git configuration, or device keychain. |
| Store LOCAL-002 backup archives in a separately selected destination rather than relying only on the live workspace's `backups/` directory. | Agreed | A secondary drive or synchronized folder can protect against loss, deletion, or corruption of the live workspace. Only completed encrypted archives may be synchronized; the live SQLite workspace must not be. |
| Support both manual and automatic LOCAL-002 backups without requiring the user to configure a schedule. | Agreed | Manual backup remains always available. Once a backup destination exists, the application may apply a sensible default schedule and must create backups before risky operations such as migrations, restore, or workspace relocation. |
| Use a modular monolith for the local MVP. | Agreed | One locally run, independently organized application is easier to install, back up, support, and evolve than microservices for one operator and 1–50 rentable spaces. |
| Prefer React/Vite and TypeScript for the interface, with Python/FastAPI, SQLAlchemy, Alembic, REST/OpenAPI, SQLite, and a workspace file store for the MVP. | Agreed | Python keeps AI-intensive document, transcription, evaluation, recommendation, and data-analysis work in the primary backend while React provides a mature interface ecosystem. |
| Defer all UI development until `UI-001`, immediately before `DASH-001`. | Agreed | The pre-UI sequence focuses on validated domain logic, persistence, APIs, CLI/setup capabilities, tests, and documentation. `UI-001` delivers the deferred Portfolio, Lease, Inspection, Finance, COM-001 communication-timeline, OWNER-003 owner-reported-rent verification, OWNER-004 owner-concern, and Maintenance workflows before the action dashboard is built. |
| Use SQLAlchemy with Alembic as the only workspace-schema authority. | Agreed | The greenfield baseline defines the complete current workspace schema, including portfolio inventory, occupancy, and availability. Future schema changes will use ordinary Alembic revisions after real customer data exists. |
| Use SQLite in WAL mode with one local writer and a SQLite-backed job/outbox mechanism. | Agreed | It supports responsive local reads and asynchronous intake/reminders without introducing Redis, a broker, or a separate database service. |
| Defer desktop packaging as a distribution choice without changing the local web application's workspace model. | Agreed | Browser-local operation can validate workflows first; a later desktop shell must retain the same external workspace, backup, and credential boundaries. |
| Provide operator-run local setup scripts for each MVP user rather than a self-service installer or updater. | Agreed | The product owner will perform setup, keeping the first release focused on management workflows rather than end-user deployment. |
| Defer authentication, cloud workspaces, and remote user access to a future SaaS offering. | Agreed | Identity and multi-tenancy are unnecessary for the single-user local MVP. |
| Support guided migration from local storage to the future SaaS offering. | Agreed | Users must be able to adopt the cloud product without re-entering records or losing financial history, attachments, or relationships. |
| Accept inbound issues through Muse Agent or manual operator entry; hold no mail or SMS-provider credentials. | Agreed — revised 2026-09-23 | Muse uses its separately authorized connections. The app retains submitted evidence, deduplicates, and requires review. SMS is forwarded to an agent-accessible source or entered manually. Native mail connector backlog items are superseded. |
| Treat COM-001 as the manual communication ledger; COM-002 drafts outbound messages for manual operator sending. | Agreed — revised 2026-09-23 | No connected sending accounts or automatic sending. Sent state records the operator's report, not confirmed delivery. INGEST-001 owns retained submitted source evidence and may link it into the timeline. |
| Monitor Muse bridge contact and reported poll failures while retaining manual entry. | Agreed — 2026-09-23 | Warn after two expected intervals without contact; a heartbeat does not prove complete ingestion. A failed poll remains visible until reported recovery. |
| Treat external account authorization separately from application authentication. | Agreed | The local MVP has no application login, but it may connect to provider APIs using credentials stored only on the operator's device. |
| Keep AI-assisted issue ingestion human-controlled. | Agreed | AI may extract fields, suggest matches and urgency, and flag duplicates, but an operator must approve or edit a draft before it becomes an official issue. |
| Include standalone voice-note issue intake with AI transcription and summarization in the MVP, without phone-call recording. | Agreed | Operators need a fast way to capture their own notes after conversations, during inspections, and on property visits. |
| Do not require preservation of source voice-note audio after successful transcription. | Agreed | The retained transcript, summary, metadata, confidence information, and operator review history are sufficient for the planned workflow and reduce local storage use. |
| Exclude external account credentials from backup and SaaS migration. | Agreed | Provider tokens are device-sensitive secrets; restored or migrated workspaces must reauthorize each external account. |
| Support self-owned, client-managed, and mixed portfolios. | Agreed | Both relationships are central to the target customer. |
| Include owner balances and manual owner-disbursement tracking in the MVP. | Agreed | Managers need to account for funds due and paid to client owners from the beginning. Electronic fund movement remains a later integration. |
| Treat FIN-002 expenses as confirmed actual spending, with Finance owning the paid amount and Maintenance retaining only estimates, quotes, and work-reported context. | Agreed | This prevents unpaid bills or duplicated maintenance cost fields from inflating financial totals; FIN-005 later owns bills, due dates, recurrence, and reminders. |
| Keep issue-backed work journals and completion outcomes append-only in Maintenance while Providers retains only clearly labeled manually entered prior-work context. | Agreed | Provider views, reporting, and AI may compose bounded source projections, but copying journal outcomes into mutable provider-history rows would create two authorities and lose provenance. |
| Keep quoted provider schedule dates separate from actual work timing. | Agreed | MAINT-002 may retain paired earliest-start and estimated-finish dates as provider-supplied comparison facts; MAINT-003 records actual occurrence and completion facts without automatically changing issue, assignment, or appointment lifecycle. |
| Create a FIN-002 expense before uploading its FILE-001 evidence, and correct an erroneous evidence association by archiving the link with a reason rather than deleting history. | Agreed | Actual spending remains recorded if an upload fails, while append-only link history preserves the audit trail and supports a clear retry workflow. |
| Put pre-move-in and post-move-out condition reports in a dedicated inspection workflow after LEASE-001. | Agreed | The lease supplies space and timing context, while condition observations, photos, acknowledgment, and comparison have an independent evidence lifecycle. |
| Keep condition classifications separate from security-deposit settlement. | Agreed | An inspection can identify possible damage, but only a later operator-reviewed finance workflow may approve a deduction, refund, deadline, or settlement. |
| Keep FIN-008 deposit funds and settlement decisions separate from rent income and property expenses. | Agreed | Deposit receipts represent held funds, not FIN-001 rent income; settlement deductions are independently entered decisions, not FIN-002 expenses, even when they cite the same evidence. FIN-003 must report these categories separately. |
| Record security-deposit deadlines and legal context without inferring statutory compliance. | Agreed | The operator supplies the property-local deadline, optional rule reference, and review notes. A later jurisdiction workflow may suggest sourced rules, but FIN-008 does not calculate law or present legal advice. |
| Require operator approval and evidence for security-deposit settlement, with immutable financial history. | Agreed | Draft deductions may be prepared without evidence, but approval requires an allowed source for every deduction and freezes exact receipt membership and arithmetic. Receipts, refunds, and approved settlements use void-and-replace corrections instead of silent edits. |
| Include owner-reported rent receipts in the MVP. | Agreed | Owners may receive rent directly; OWNER-003 keeps the report and evidence as provenance but counts income only through one linked FIN-001 receipt. Verification must adopt a compatible receipt or create one atomically through Finance, never use the independent-duplicate override, and later owner balances treat an active verified link as funds already held by that client owner. |
| Keep client-owner operational concerns in a dedicated owner-management aggregate. | Agreed | OWNER-004 preserves who raised a general rental, lease, tenant, or vacancy concern and its independent lifecycle. Communications owns interactions, Tasks owns actions, source modules own their facts, and owner-accounting remains financial. |
| Apply OWNER-004 only to a selected effective client-owner Party. | Agreed | PORT-001 intentionally represents local-operator ownership without a Party ID. Mixed properties use the specifically selected client owner; the product never fabricates an owner Party or treats operational ownership context as a legal conclusion. |
| Include manual rental applications, applicant financial evidence, and human lease-approval decisions in the MVP. | Agreed | Small operators need the qualification record connected to the lead and eventual lease even before third-party screening integrations are added. |
| Record lawful household occupancy needs, but never use protected familial status as an approval criterion. | Agreed | Residential screening must support lease administration without enabling discriminatory decisions. |
| Record credit scores, income, obligations, and asset evidence with consent, source, verification, redaction, and retention or deletion metadata. | Agreed | Bank and brokerage statements and consumer-report data are sensitive and must be handled for a documented housing purpose. |
| Record an immutable actual payment-method snapshot on each rent receipt, including externally arranged automatic bank payments. | Agreed | FIN-006 records how a receipt was paid, uses only safe masked references, and never maintains expected-method state, initiates a transfer, or stores bank credentials. The UI may prefill from the last non-voided receipt only as editable convenience. |
| Track one future-dated prepaid check for one complete rent-expectation period and remind the operator when it may be deposited. | Agreed | FIN-007 owns a safe masked check lifecycle, a property-local reminder, and correlated deposit/return handoffs. A scheduled check is not income; a return voids its linked FIN-001 receipt, while replacement preserves nonbranching history. |
| Add configurable provider categories in the MVP. | Agreed | Categories such as legal, landscaping, electrical, HVAC/A/C, appliance repair, and plumbing make provider search and issue routing practical. |
| Keep Maintenance issue categories, VEND-001 free-form provider service labels, and future VEND-CAT-001 provider categories distinct until an explicit mapping is designed. | Agreed | Similar labels do not establish equivalent taxonomies. MAINT-002 may show provider service and area context, but it must not infer category compatibility or silently rewrite issue or provider history. |
| Alert on rent-adjustment notice deadlines using confirmed, sourced, effective-dated local jurisdiction rules. | Agreed | Legal deadlines can change, so the application must expose its source and verification date and require operator confirmation rather than present legal advice. |
| Let AI suggest issue diagnoses, clarifying questions, safety escalation, and suitable saved providers in the MVP. | Agreed | The suggestions can accelerate triage, but a human remains responsible for the diagnosis, response, provider contact, and assignment. |
| Capture whether a property issue was raised by an owner, tenant, manager, or staff member. | Agreed | Source attribution affects communication, responsibility, follow-up, and reporting. |
| Have the local MVP operator record owner- and tenant-reported items with source attribution. | Agreed | Direct submissions require remote access and authentication controls and therefore belong to the future SaaS offering. |
| Support single-family homes, condos, townhomes, and offices in the MVP. | Agreed | Covers initial residential and office needs while keeping operating models manageable. |
| Defer multi-unit apartment-building operations. | Agreed | Apartment-specific needs such as common areas, bulk actions, and turnover workflows are not needed initially. |
| Use a shared property/space model that can later represent apartment units. | Agreed | Avoids a costly future data-model rewrite without exposing apartment complexity now. |
| Include approved document templates, AI document drafting/review, AI listing drafts, and AI maintenance triage/provider recommendations in the MVP. | Agreed | These capabilities now have source records, approval controls, and operating history available in the MVP; showing coordination, negotiation drafting, and broader risk recommendations remain post-MVP. |
| Move the remaining AI recommendation backlog from Later to Next. | Agreed | Rent and renewal recommendations plus vacancy and delinquency risk should follow the MVP, rather than wait for later local-product extensions. |
| Treat AI as a drafting and review assistant, never an autonomous sender or signer. | Agreed | Maintains operator control for contracts, marketing, scheduling, and negotiations. |
| Track external vendor reputation with links and user-entered observations before automating sources. | Agreed | Avoids dependency, cost, and terms-of-service risk in the MVP. |
| Make report drill-down mandatory. | Agreed | Trust in financial and operational reporting depends on seeing the source records. |
| Use plain-language labels rather than accounting or CRM jargon. | Agreed | The product is intended for nontechnical users. |
| Adopt the [confirmed UI-001 operator design](UI-001_DESIGN.md), approved September 23, 2026. | Agreed | Consolidates the product interview, screen refinements, domain boundaries, and acceptance scenarios; backend prerequisites remain explicitly unimplemented until delivered. |
| Provide configurable Home, Properties, Owners, Leasing, Money, Maintenance, and Providers destinations, with Light/Dark Settings. | Agreed | Operators can hide/reorder destinations without concealing obligations; directories and contextual workspaces support both portfolio-wide work and owner/property review. Home and Settings remain accessible. |
| Make the entire non-editable item summary bar toggle its details below. | Agreed | No inputs or separate actions belong in the bar. Explain the behavior visibly, support keyboard disclosure, retain independent expansions and drafts, and put editing/commit actions inside expanded content or dedicated workflow pages. |
| Separate Needs action, Waiting, Upcoming, appointments, and information coverage. | Agreed | An empty queue does not prove complete information. Follow-up changes never rewrite obligation deadlines or hide urgent unresolved work; missing/unavailable data is not a zero. |
| Include manual eviction/legal-matter tracking with attorney links in MVP. | Agreed | Keep broad case status separate from evidence-backed milestones and confirmed deadline sources. Case closure does not imply lease termination, move-out, or financial changes; automated legal interpretation is deferred. |
| Include HOA violation notices and narrow HOA-covered shared-repair coordination in MVP; defer broader HOA administration. | Agreed | Preserve notice history and closure evidence. For a common-element repair, use one Maintenance-owned case across affected managed units, preserve every association contact and follow-up, and require physical verification. HOA acknowledgement does not resolve the repair, prove accepted coverage, or create an expense or tenant liability. Standing rules, architectural approvals, assessments, and board administration remain later work. |
| Include Excel and direct read-only Google Sheets snapshot imports for properties, owners, and providers in MVP. | Agreed | Review column mappings, duplicates, and ownership links before create/link/skip operations. Do not silently overwrite, merge, write to source sheets, or continuously synchronize. Preserve row-level results and duplicate-safe retries; broader history/update migration stays later. |
| Use a provider-neutral `AiProviderPort` with fixed Meta Muse product identity and Meta Model API inference. | Agreed — revised 2026-09-23 | Domain modules never call model transports directly. Generated runs record Meta Model API and the actual Muse model/version. The UI has no provider selector; personal-agent access is a separate MCP grant. |
| Apply versioned PII redaction profiles to every AI input, prepared by the owning module. | Agreed | Tenant and owner message content sent to a cloud model must be minimized: no raw bank data, no unredacted account identifiers, applicant financial evidence only with consent metadata. |
| Keep the Meta Model API key and Muse bridge credentials separate in the OS credential store, keyed to workspace ID and excluded from portable data. | Agreed — revised 2026-09-23 | A model key does not authorize the personal agent. Credentials never enter the database, backups, exports, audit snapshots, logs, or SaaS migration; restore requires fresh configuration/authorization. |
| Provide a local MCP server for conversational assistance with read/query tools and proposal-only writes routed through the AI review queue. | Agreed | Lets a Muse assistant work over workspace records without direct write access; every proposed change remains an operator-approved draft. |
| Enforce per-action AI limits with one operator kill switch; use only measurable limits for external proposals. | Agreed — revised 2026-09-23 | Generated runs have daily and token ceilings plus registered Muse model restrictions. External proposals have admission caps and payload ceilings; missing Muse token usage remains unknown. Violations fail closed. |
