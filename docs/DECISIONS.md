# Product Decisions

| Decision | Status | Rationale |
| --- | --- | --- |
| Serve independent landlords and property managers with approximately 1–50 rentable spaces. | Agreed | Keeps workflows practical and avoids enterprise-first complexity. |
| Run the MVP locally for one operator without authentication. | Agreed | The initial product should validate the core property-management workflows without SaaS account, hosting, or collaboration complexity. |
| Store MVP records and attachments locally with backup/export and restore. | Agreed | Local operation needs a clear durability and recovery path. |
| Keep each user's configurable workspace outside the Git-maintained application checkout. | Agreed | Code, migrations, templates, and setup tools belong in Git; real records, SQLite files, attachments, backups, and exports must not. |
| Use a Git-ignored local workspace locator at `application/config.local.json` and a versioned non-secret workspace manifest. | Agreed | The locator identifies the selected external folder without committing user data; the manifest gives the portable workspace a stable identity and format version. |
| Reference attachments relative to the workspace and move workspaces through a copy-and-verify workflow. | Agreed | Relative references support relocation, restore, export, and future SaaS migration without broken absolute paths or incomplete moves. |
| Use SQLite-consistent backups for a live workspace and keep connection credentials in the OS credential store. | Agreed | Copying only an open SQLite database file can be incomplete; external-account tokens are device-sensitive secrets and do not belong in backups or exports. |
| Require passphrase-based authenticated encryption for portable LOCAL-002 backup and export archives. | Agreed | Backups will contain sensitive leases, financial records, and future applicant evidence; a portable archive must remain recoverable on another machine without storing its passphrase in the workspace, Git configuration, or device keychain. |
| Store LOCAL-002 backup archives in a separately selected destination rather than relying only on the live workspace's `backups/` directory. | Agreed | A secondary drive or synchronized folder can protect against loss, deletion, or corruption of the live workspace. Only completed encrypted archives may be synchronized; the live SQLite workspace must not be. |
| Support both manual and automatic LOCAL-002 backups without requiring the user to configure a schedule. | Agreed | Manual backup remains always available. Once a backup destination exists, the application may apply a sensible default schedule and must create backups before risky operations such as migrations, restore, or workspace relocation. |
| Use a modular monolith for the local MVP. | Agreed | One locally run, independently organized application is easier to install, back up, support, and evolve than microservices for one operator and 1–50 rentable spaces. |
| Prefer React/Vite and TypeScript for the interface, with Python/FastAPI, SQLAlchemy, Alembic, REST/OpenAPI, SQLite, and a workspace file store for the MVP. | Agreed | Python keeps AI-intensive document, transcription, evaluation, recommendation, and data-analysis work in the primary backend while React provides a mature interface ecosystem. |
| Defer all UI development until `DASH-001`. | Agreed | The pre-dashboard sequence focuses on validated domain logic, persistence, APIs, CLI/setup capabilities, tests, and documentation; React screens and shared web packages begin only when the action dashboard is ready to anchor the operator experience. |
| Use SQLAlchemy with Alembic as the only workspace-schema authority. | Agreed | The greenfield baseline defines the complete current workspace schema, including portfolio inventory, occupancy, and availability. Future schema changes will use ordinary Alembic revisions after real customer data exists. |
| Use SQLite in WAL mode with one local writer and a SQLite-backed job/outbox mechanism. | Agreed | It supports responsive local reads and asynchronous intake/reminders without introducing Redis, a broker, or a separate database service. |
| Defer desktop packaging as a distribution choice without changing the local web application's workspace model. | Agreed | Browser-local operation can validate workflows first; a later desktop shell must retain the same external workspace, backup, and credential boundaries. |
| Provide operator-run local setup scripts for each MVP user rather than a self-service installer or updater. | Agreed | The product owner will perform setup, keeping the first release focused on management workflows rather than end-user deployment. |
| Defer authentication, cloud workspaces, and remote user access to a future SaaS offering. | Agreed | Identity and multi-tenancy are unnecessary for the single-user local MVP. |
| Support guided migration from local storage to the future SaaS offering. | Agreed | Users must be able to adopt the cloud product without re-entering records or losing financial history, attachments, or relationships. |
| Ingest issue messages from Gmail, Outlook.com/Hotmail, and SMS sources in the MVP. | Agreed | Owners and tenants often report issues through existing communication channels, so the local operator needs one review queue. |
| Treat external account authorization separately from application authentication. | Agreed | The local MVP has no application login, but it may connect to provider APIs using credentials stored only on the operator's device. |
| Keep AI-assisted issue ingestion human-controlled. | Agreed | AI may extract fields, suggest matches and urgency, and flag duplicates, but an operator must approve or edit a draft before it becomes an official issue. |
| Include standalone voice-note issue intake with AI transcription and summarization in the MVP, without phone-call recording. | Agreed | Operators need a fast way to capture their own notes after conversations, during inspections, and on property visits. |
| Do not require preservation of source voice-note audio after successful transcription. | Agreed | The retained transcript, summary, metadata, confidence information, and operator review history are sufficient for the planned workflow and reduce local storage use. |
| Exclude external account credentials from backup and SaaS migration. | Agreed | Provider tokens are device-sensitive secrets; restored or migrated workspaces must reauthorize each external account. |
| Support self-owned, client-managed, and mixed portfolios. | Agreed | Both relationships are central to the target customer. |
| Include owner balances and manual owner-disbursement tracking in the MVP. | Agreed | Managers need to account for funds due and paid to client owners from the beginning. Electronic fund movement remains a later integration. |
| Put pre-move-in and post-move-out condition reports in a dedicated inspection workflow after LEASE-001. | Agreed | The lease supplies space and timing context, while condition observations, photos, acknowledgment, and comparison have an independent evidence lifecycle. |
| Keep condition classifications separate from security-deposit settlement. | Agreed | An inspection can identify possible damage, but only a later operator-reviewed finance workflow may approve a deduction, refund, deadline, or settlement. |
| Include owner-reported rent receipts in the MVP. | Agreed | Owners may receive rent directly; source and verification tracking prevent omissions and duplicate income. |
| Include manual rental applications, applicant financial evidence, and human lease-approval decisions in the MVP. | Agreed | Small operators need the qualification record connected to the lead and eventual lease even before third-party screening integrations are added. |
| Record lawful household occupancy needs, but never use protected familial status as an approval criterion. | Agreed | Residential screening must support lease administration without enabling discriminatory decisions. |
| Record credit scores, income, obligations, and asset evidence with consent, source, verification, redaction, and retention or deletion metadata. | Agreed | Bank and brokerage statements and consumer-report data are sensitive and must be handled for a documented housing purpose. |
| Track expected and actual rent-payment methods, including externally arranged automatic bank payments. | Agreed | The MVP needs an accurate operational record without initiating transfers or storing bank credentials. |
| Track future-dated prepaid checks and remind the operator when the current check may be deposited. | Agreed | A check schedule prevents missed deposits while avoiding premature recognition of undeposited funds as received income. |
| Add configurable provider categories in the MVP. | Agreed | Categories such as legal, landscaping, electrical, HVAC/A/C, appliance repair, and plumbing make provider search and issue routing practical. |
| Alert on rent-adjustment notice deadlines using confirmed, sourced, effective-dated local jurisdiction rules. | Agreed | Legal deadlines can change, so the application must expose its source and verification date and require operator confirmation rather than present legal advice. |
| Let AI suggest issue diagnoses, clarifying questions, safety escalation, and suitable saved providers in the MVP. | Agreed | The suggestions can accelerate triage, but a human remains responsible for the diagnosis, response, provider contact, and assignment. |
| Capture whether a property issue was raised by an owner, tenant, manager, or staff member. | Agreed | Source attribution affects communication, responsibility, follow-up, and reporting. |
| Have the local MVP operator record owner- and tenant-reported items with source attribution. | Agreed | Direct submissions require remote access and authentication controls and therefore belong to the future SaaS offering. |
| Support single-family homes, condos, townhomes, and offices in the MVP. | Agreed | Covers initial residential and office needs while keeping operating models manageable. |
| Defer multi-unit apartment-building operations. | Agreed | Apartment-specific needs such as common areas, bulk actions, and turnover workflows are not needed initially. |
| Use a shared property/space model that can later represent apartment units. | Agreed | Avoids a costly future data-model rewrite without exposing apartment complexity now. |
| Include approved document templates, AI document drafting/review, AI listing drafts, and AI maintenance triage/provider recommendations in the MVP. | Agreed | These capabilities now have source records, approval controls, and operating history available in the MVP; showing coordination, negotiation drafting, and broader risk recommendations remain post-MVP. |
| Move the remaining AI recommendation backlog from Later to Next. | Agreed | Rent and renewal recommendations plus vacancy and delinquency risk should follow the MVP, rather than wait for later local-product extensions. |
| Treat AI as a drafting and review assistant, never an autonomous sender or signer. | Agreed | Maintains operator control for contracts, marketing, scheduling, and negotiations. |
| Track external vendor reputation with links and user-entered observations before automating sources. | Agreed | Avoids dependency, cost, and terms-of-service risk in the MVP. |
| Make report drill-down mandatory. | Agreed | Trust in financial and operational reporting depends on seeing the source records. |
| Use plain-language labels rather than accounting or CRM jargon. | Agreed | The product is intended for nontechnical users. |
