# AUDIT-001 — Local Audit Ledger Design

## Purpose

`AUDIT-001` provides trustworthy record history for a single local operator. It must show what changed, when it changed, what the prior values were, why the change was made when a reason is supplied, and whether the change originated with the operator, a connector, an AI-assisted draft/review, or an automated local process.

It is an audit and recovery aid, not a substitute for legal record-retention advice, a multi-user permission system, or tamper-proof regulatory evidence. The MVP has no application login, so events identify the local operator or an operational source rather than a user account.

## Scope

The ledger is required for sensitive records, including:

- Rent expectations, payments, payment methods, expenses, owner balances, owner-reported receipts, and owner disbursements.
- Leases, deposits, renewal/rent-adjustment terms, notices, approvals, and important documents.
- Owner, tenant, applicant, provider, issue, quote, work-journal, and communication records where later modules designate fields as sensitive.
- Ingested messages, attachments, voice-note transcripts, AI output, and operator review or approval decisions.
- System actions that materially affect data, such as import, restore, migration, retention/deletion, connector reconciliation, and automatic backup outcome.

Routine non-sensitive presentation preferences and temporary client-side form state are out of scope.

## Data model

Create an append-only `audit_events` table in the workspace database. It is independent of individual domain tables so every MVP module can use one consistent history format. The initial platform migration is versioned, records its applied version, takes a SQLite-consistent private migration-safety snapshot before changing the schema, and writes an audit migration outcome. It runs as one explicit SQLite transaction; failed validation or migration leaves the live schema unchanged.

| Field | Meaning |
| --- | --- |
| `id` | Stable UUID for migration and cross-record references. |
| `occurred_at` | UTC timestamp generated by the application transaction. |
| `entity_type`, `entity_id` | Stable type and ID of the affected domain record. |
| `action` | `created`, `updated`, `deleted`, `restored`, `status_changed`, `approved`, `rejected`, `imported`, `ingested`, `ai_draft_created`, `ai_reviewed`, or a documented module-specific action. |
| `before_snapshot` | Canonical JSON snapshot before the action; null for creation. |
| `after_snapshot` | Canonical JSON snapshot after the action; null for deletion. |
| `changed_fields` | JSON list of changed field paths, computed from snapshots for readable drill-down. |
| `reason` | Optional human-entered reason or a bounded system reason code. |
| `actor_kind` | `local_operator`, `system`, `connector`, or `ai_assistant`. |
| `actor_reference` | Optional non-secret source reference, such as connector name/source message ID or model-run ID. |
| `correlation_id` | UUID shared by one business operation and its related events. |
| `schema_version` | Version of the snapshot shape for portable migration and future rendering. |

Snapshots contain stored domain values, not computed balances or derived display fields. File-bearing records store portable file metadata—relative path, content hash, media type, and original name where appropriate—not file bytes. Secret tokens, passphrases, raw payment credentials, and unredacted account identifiers are never written to audit snapshots.

Sensitive data already needed by the business record can appear in a protected audit snapshot because retaining prior values is the purpose of the ledger. The local workspace’s access controls, encrypted portable backups, and future retention policies protect it. UI output must apply the same redaction rules as the owning domain module.

## Write rules

1. A domain write and its audit event occur in the same SQLite transaction. Either both commit or neither commits.
2. Domain application services own the business change; a shared `AuditRecorder` receives an explicit audit context and serializable before/after values. Repositories must not silently mutate sensitive records outside that boundary.
3. Creation records the full initial `after_snapshot`. Update records retain both snapshots and changed paths. Deletion records retain the full `before_snapshot`; sensitive domains should use a reversible status/void action instead of physical deletion where practical.
4. Audit events are append-only. SQLite triggers reject `UPDATE` and `DELETE` against `audit_events` during ordinary application operation. The application never exposes an edit or delete audit endpoint.
5. Bulk/import/restore work emits one correlation ID and one event per changed entity, plus a bounded operation-summary event. This preserves drill-down without placing an unbounded payload in one row.
6. Failed transactions do not generate successful change events. Operational failures are logged separately and may create an audit event only when they alter stored state.

Direct modification of a local SQLite file outside the application cannot be made impossible in the MVP. The append-only database controls, workspace permissions, server lifetime lock, encrypted backups, and restore validation make ordinary accidental changes detectable and recoverable; a future SaaS deployment adds server-side access control and stronger tamper evidence.

## Application interfaces

Introduce these focused interfaces rather than a generic cross-domain “service” dump:

- `AuditEvent` domain value and action vocabulary.
- `AuditRecorder` application port: record one or many events within an existing transaction.
- `AuditHistoryRepository` infrastructure port: append and query events by entity, correlation ID, action, actor, and time range.
- `AuditSnapshotPolicy` owned by each domain: defines auditable fields, recursive secret/account-identifier rejection, presentation redaction rules, and snapshot schema version. The shared default is deliberately conservative; a sensitive module supplies an allowlist and its own UI redaction policy before it writes events.

Each sensitive module calls the recorder from its own use case. The audit module does not decide whether a rent increase is allowed, whether an issue is urgent, or how an approval works.

## User experience

Every sensitive record gets a plain-language **History** view:

- A chronological timeline with time, action, source, optional reason, and a concise summary such as “Rent changed from $1,800 to $1,900.”
- A drill-down comparison showing before/after fields with domain redaction applied.
- Links to related records, attachments, source messages, AI reviews, or operation correlation history when available.
- Read-only presentation: no “edit history” control.

The MVP also offers a global **Activity history** filter for property, record type, date range, source, and action. It is a support and investigation tool, not an accounting report. Financial reports continue to drill down to the actual financial records, then into history.

## AI and ingestion behavior

AI output and imported messages do not overwrite a source record invisibly. The ledger records source ingestion, draft creation, edits to the editable draft, the human approval/rejection decision, and the resulting official record. `actor_kind` makes it clear which data originated from a connector, AI assistant, system process, or local operator.

Voice-note audio remains optional input material. If it is discarded after transcription, the audit event retains the transcript/summary references and the review decision, never a claim that the discarded audio is still available.

## Retention and recovery

The initial MVP does not automatically purge audit events. A later retention feature may remove or redact sensitive business evidence according to an explicit, reviewed policy; it must preserve an append-only event explaining the retention action without retaining the removed secret or evidence itself.

Audit events live in the SQLite database and therefore participate in `LOCAL-002` backup, export, validation, restore, and future SaaS migration. Stable event IDs, entity IDs, timestamps, snapshot schema versions, and correlation IDs must survive those flows.

## Implementation sequence

1. Add the audited schema migration and append-only triggers, together with a migration/transaction foundation compatible with SQLite now and PostgreSQL later.
2. Implement the audit domain types, recorder, repository, snapshot serialization, and record-history query API.
3. Add a minimal read-only History API and UI shell with a sanitized fixture entity to verify end-to-end behavior.
4. Require new sensitive modules to provide an `AuditSnapshotPolicy`; introduce audit events with each module rather than retroactively guessing missing history.
5. Add global activity filters, import/restore correlation handling, and richer domain-specific summaries as those modules arrive.

## Acceptance criteria

`AUDIT-001` is complete when:

1. A transaction that creates, changes, voids/deletes, restores, approves, or rejects a designated sensitive test record writes the correct append-only event in the same transaction.
2. Each event retains the prior values required to explain the change, a portable after value where applicable, changed paths, timestamp, source/actor, and correlation ID.
3. Direct application attempts to update or delete an audit event fail with a controlled database error.
4. A read-only history query returns ordered record history and a field-level redacted before/after comparison.
5. Connector and AI-assisted test flows visibly distinguish source ingestion, draft/review, human decision, and official-record creation.
6. Audit rows appear in encrypted backup/export archives and survive restore with stable IDs and relationships.
7. Tests cover transaction rollback, bulk-operation correlation, redaction, append-only enforcement, and portable snapshot serialization.
