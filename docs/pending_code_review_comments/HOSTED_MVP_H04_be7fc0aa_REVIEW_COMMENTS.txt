Host Agent, manual provisioning and admin schema

1. [P1] WorkspaceService.initialize() deletes and replaces workspace_root, stripping ext4 prjquota and ownership set by prepare_resources
File: application/apps/server/app/modules/host_agent/infrastructure/manual_provision.py:99-108
Related: application/apps/server/app/modules/workspace/application/service.py:92,177-194

ManualProvisioner.provision() invokes self.host_effect_hook("prepare_resources", intent, paths) (line 102) to apply UID/GID ownership and ext4 project quota (FS_PROJINHERIT_FL + project ID) onto paths.workspace_root, and then calls ws_service.initialize() (line 108). WorkspaceService.initialize() creates a sibling staging directory under paths.workspace_root.parent (outside the project quota), then executes self.paths.root.rmdir() followed by staging_paths.root.replace(self.paths.root) (service.py:191-193). Replacing paths.workspace_root with a new directory inode from the parent destroys the ext4 project ID, FS_PROJINHERIT_FL, and per-operator ownership established by prepare_resources (or fails if workspace_root is non-removable). Subsequent workspace files and property-management.sqlite silently escape the workspace ext4 project quota or fail RuntimeEffects.guard()/storage.verify() at start_container. Initialize the workspace layout and database in place inside the already-prepared paths.workspace_root (without rmdir/replace on workspace_root itself) so created files inherit the ext4 project ID.

2. [P2] capacity_profiles single-column primary key prevents inserting new profile_revision rows on an immutable table
File: application/database/admin-migrations/versions/admin_0001_initial.py:175-188,596

capacity_profiles declares f("profile_ref", "REF", primary=True) as a single-column primary key while also defining sa.UniqueConstraint("profile_ref", "profile_revision") (line 187), a composite FK (profile_ref, profile_revision) from capacity_snapshots (lines 200-203), and append-only immutability via immutable(op, "capacity_profiles") (line 596). Because profile_ref alone is the PK and rows cannot be updated or deleted, appending a new profile_revision for an existing profile_ref always fails with IntegrityError ("retained hosted identity"). Make (profile_ref, profile_revision) the composite primary key and remove the redundant UniqueConstraint.

3. [P2] Concurrent ManualProvisioner.provision() race and mark_succeeded() caught by mark_needs_attention(unknown=False) fallback
File: application/apps/server/app/modules/host_agent/infrastructure/manual_provision.py:88-96,146-184
Related: application/apps/server/app/modules/hosted_admin/infrastructure/provisioning_admission.py:27,254-276,326,456-459

(a) AdminEffectAdmission.mark_running() allows "running" in ADMITTABLE_STATES, so two concurrent ManualProvisioner.provision(operation_id) calls both pass mark_running() and concurrently mutate the same workspace.sqlite, access.sqlite, seed-journal.json, and host effect hooks.
(b) self.admission.mark_succeeded(...) (lines 150-155) sits inside the try block whose except Exception: handler unconditionally calls self.admission.mark_needs_attention(..., unknown=False) (lines 173-178). If a concurrent run already transitioned the operation to 'succeeded', mark_succeeded raises HostAgentDenied, which enters except Exception: and calls mark_needs_attention, raising an unhandled HostAgentDenied instead of returning the succeeded outcome. If start_container or mark_succeeded fails ambiguously after external host effects (apply_auth_routes, start_container) have started, unknown=False records needs_attention / capacity_commitments.state='pending' instead of 'unknown'.
Guard against concurrent execution of the same operation_id (reject running -> running in mark_running or take an exclusive per-operation lock), handle already-succeeded races cleanly, and record unknown=True when an error occurs after irreversible/external host effects have begun.

Hosted access, source lifecycle and Free storage admission

10. [P1] Stale-measurement overwrite and concurrent reservation-release race in UsageAccountingStore
File: application/apps/server/app/modules/hosted_access/infrastructure/usage_accounting.py:151-208,335-379,420-461

refresh_usage_state, settle_commit, and reconcile_unknown all run measure_logical_usage(self.business_engine) outside immediate_transaction(self.access_engine) and then unconditionally overwrite main.usage_state inside the transaction.
(a) Stale overwrite: If operation A measures business.sqlite before operation B commits, and B settles first (usage_state = 20 MB, B's reservation committed), A then enters immediate_transaction(self.access_engine) and overwrites usage_state with A's older, smaller measurement while marking A's reservation committed (reserved_bytes = 0). Logical usage is permanently undercounted, allowing subsequent writes to bypass the 50,000,000-byte Free quota.
(b) Premature release in reconcile_unknown: Any reservation that commits to business.sqlite and transitions to 'unknown' (or is created as 'held' when include_held=True) between measure_logical_usage and UPDATE main.usage_reservations SET state='released' WHERE state IN ... is released even though its bytes were excluded from the measurement.
Run measure_logical_usage(self.business_engine) inside immediate_transaction(self.access_engine) (WAL-mode reads on business.sqlite serialize against usage_state updates via the access.sqlite immediate lock), or guard usage_state updates with an optimistic revision check + retry loop and restrict reconcile_unknown to the exact reservation_id set observed prior to measurement.

11. [P2] asyncio.CancelledError (and settle_commit failure) permanently leaks 'held' reservations in FreeStorageAdmission
File: application/apps/server/app/modules/hosted_access/infrastructure/free_storage_admission.py:115-130
Related: application/apps/server/app/modules/hosted_access/api/managed_business.py:226-238

reserve_request catches HostedAccessError and Exception, but not BaseException. In Python 3.8+, asyncio.CancelledError (triggered on client disconnect / ASGI cancellation during await app(...)) inherits from BaseException. When cancelled, neither release nor mark_unknown runs, leaving the row stuck in state='held'. Because reconcile_unknown() defaults to include_held=False, leaked 'held' rows permanently consume the 50 MB Free quota. Likewise, an exception inside settle_commit() in the else: branch leaves the reservation 'held'. Catch BaseException (after HostedAccessError) to call mark_unknown before re-raising, and wrap settle_commit() so failures also transition the reservation to 'unknown'.

16. [P3] Backwards wall-clock step violates ck_reservation_time (updated_at >= created_at)
