1. [P0] Cross-DEK chunk deduplication collision silently publishes unrestorable verified backup points
File: application/apps/server/app/modules/hosted_recovery/infrastructure/engine.py:105-125,148-160,180-192,231-236,334-340,480-490
Related: application/apps/server/app/modules/workspace/infrastructure/hosted_recovery.py:1106-1110; application/apps/server/app/modules/hosted_admin/infrastructure/admin_recovery.py:535-540

_obtain_dek() generates a fresh random 32-byte DEK whenever existing_wrapped_dek_b64 is None. Callers only cache _last_wrapped_dek_b64 in memory, so any container restart, deploy, or repair_runtime resets it to None. Chunk object keys are namespaced only by key_fingerprint(context.key_ref) (chunks/{key_fp}/{chunk_sha256}.enc), not by DEK identity. When head_object(object_key) reports head.exists == True (lines 150-160, 182-192), _upload_file_chunks() skips uploading and records the pre-existing chunk (encrypted under an earlier DEK) in the new manifest (which wraps the new DEK). Because default full_readback=False only runs head_object on deduplicated chunks (lines 480-490), verify_point() passes and publishes a "verified" point whose manifest DEK cannot decrypt its deduplicated chunks (restore_point() fails with RecoveryCryptoError / InvalidTag). In AdminControlRecoveryService (full_readback=True), every backup after a restart fails permanently whenever any chunk matches an existing chunk in R2 under the same key_ref.
Namespace chunk keys by a DEK-derived fingerprint in addition to key_fp (e.g., chunks/{key_fp}/{dek_fp}/{chunk_sha256}.enc) so distinct DEKs can never collide, and reload existing_wrapped_dek_b64 from the latest verified manifest/store on startup when key_ref is unchanged to preserve cross-restart deduplication.

2. [P1] BackupProxyHandler.list_objects overflows the 16 KiB frame header at ~173 chunks and drops the connection
File: application/apps/server/app/modules/host_agent/infrastructure/backup_proxy.py:47,271-278,309-318,356-359

BackupProxyHandler.dispatch() returns {"ok": True, "keys": relative_keys}, b"" (line 278), placing the entire key list in the JSON header, which is capped at MAX_HEADER_BYTES = 16 * 1024 (line 47). Each chunk key is ~92 bytes (~95 bytes in JSON), so at ~173 keys (~43 MiB at default 256 KiB chunks, below the 50 MB Free allowance), _send_frame() raises BackupProxyUnavailable. Because _send_frame() at lines 356-359 is outside the except HostedRecoveryError handler and only catches OSError, the exception escapes into ThreadPoolExecutor and abruptly closes the socket.
Serialize the list_objects key payload in response_body (bounded by MAX_BODY_BYTES) instead of response_header, and catch HostedRecoveryError around response framing so a bounded error header is returned instead of EOF.

3. [P2] Slowloris worker-pool starvation and unbounded connection queue in BackupProxyServer
File: application/apps/server/app/modules/host_agent/infrastructure/backup_proxy.py:297-306,339-345,407,415-424

BackupProxyServer uses ThreadPoolExecutor(max_workers=8) (line 407) with an unbounded queue and accepts connections without concurrency limits (lines 418-423). handle_proxy_connection() sets a per-recv() timeout of 15s (line 341), while _recv_exact() loops without a total request deadline (lines 297-306).
