[P2] 1. GET /health and GET /api/workspace run full 18-module schema+data validation and chmod syscalls on every request
Files:
- application/apps/server/app/modules/workspace/api/router.py:40-73
- application/apps/server/app/modules/workspace/application/service.py:132-171
- application/apps/server/app/platform/product_migrations.py:101-284
Defect:
Both health() (router.py:45) and workspace_status() (router.py:66) invoke service.open() on every HTTP request even when runtime.start() / runtime.refresh() has already opened and validated the workspace with integrity_check=True. Each service.open() creates and disposes a fresh SQLAlchemy engine, runs validate_latest_schema() across all 18 module schema and full-table data validators, and calls _secure_existing_workspace_paths() (chmod 0700/0600 on workspace directories and SQLite/WAL/SHM files).
Impact:
On a populated workspace, every health check or workspace status poll triggers full-table scans across 100+ tables and repeated filesystem permission mutations, degrading latency and adding SQLite read contention.
Fix:
When runtime is present and runtime.ready is True, serve /health and /api/workspace from the validated runtime manifest/state (or a lightweight manifest/DB presence check), reserving full validate_latest_schema() for startup, refresh(), backup, and restore.

[P2] 2. FileStorageVerificationService.verify() re-hashes/re-downloads every workspace file on every S3 reconciliation continuation page
Files:
- application/apps/server/app/modules/files/application/verification.py:51-156
Defect:
verify(file_id=None, continuation=...) unconditionally loops over all candidates from files_for_verification() (lines 57-103), hashing every local file or downloading and hashing every S3 object and writing a storage_verified audit event on every paginated continuation request.
Impact:
When S3 inventory reconciliation spans N pages (>1,000 object versions), resuming verification via continuation re-downloads, re-hashes, and re-audits every file in the workspace N times (O(N * files)), multiplying S3 egress, disk I/O, audit-table growth, and request latency.
Fix:
Run the per-file content verification pass only on the initial call (continuation is None), carry content-problem counts in the continuation token, and advance only the paginated S3 reconciliation on subsequent continuation calls.

[P2] 3. FileService.upload() double-rolls back and masks cleanup errors when content.rollback() fails after an idempotent replay
Files:
- application/apps/server/app/modules/files/application/service.py:249-274
Defect:
When an upload hits an existing idempotency key inside persist() (replayed = True), line 250 sets committed = False and line 252 calls content.rollback(). If that rollback() raises, execution enters except BaseException as error: (line 256) where not committed is True, calling content.rollback() a second time at line 260. If the second rollback() succeeds, line 274 re-raises the original cleanup error instead of returning the replayed result or recording PublicationCleanupIncomplete.
Impact:
Transient cleanup errors on idempotent upload replays issue duplicate delete_object/unlink calls and can turn an already-committed replayed upload into an unhandled 500 without recording cleanup attention.
Fix:
Wrap the replay-path content.rollback() in its own try/except block that records PublicationCleanupIncomplete on failure, and clear content = None before returning result so the outer handler never retries rollback on a replay path.

[P2] 4. BackupService._audit() and _audit_restored_workspace() leak open sqlite3.Connection handles
Files:
- application/apps/server/app/modules/workspace/application/backup_service.py:425, 441, 467
Defect:
All three methods use `with sqlite3.connect(...) as connection:` without `contextlib.closing(...)`. Python's sqlite3 connection context manager only commits/rolls back transactions on exit and does not close the underlying connection or file descriptor.
Impact:
Every backup audit, retention audit, idempotent audit conflict check, and restore audit leaks an open SQLite file descriptor until garbage collection.
Fix:
Wrap each sqlite3.connect(...) in contextlib.closing(...) (matching SQLiteWorkspaceStore and SQLiteAuditRepository), e.g., `with closing(sqlite3.connect(...)) as connection, connection:`.

[P1] 12. SQLiteMaintenanceUnitOfWork uses raw create_engine() instead of create_sqlite_engine(), bypassing FK enforcement, BEGIN IMMEDIATE, and attempt-fence error mapping
Files:
- application/apps/server/app/modules/maintenance/infrastructure/unit_of_work.py:13, 1226-1268
Reference:
- application/apps/server/app/platform/sqlite_engine.py:15-47, 71-91
Defect:
SQLiteMaintenanceUnitOfWork.write() (line 1227) and read() (line 1249) construct a fresh engine via `create_engine(f"sqlite:///{self.database}")` instead of holding a shared `create_sqlite_engine(database)`. As a result, none of the engine listeners installed by create_sqlite_engine() are attached:
1. `PRAGMA foreign_keys = ON` is never executed on maintenance connections, leaving all maintenance foreign keys unenforced at write time.
2. The `begin` event listener is absent, so `immediate_transaction(engine)` sets `connection.info["sqlite_immediate"] = True` with no listener to emit `BEGIN IMMEDIATE` (writes run as deferred transactions).
3. The `handle_error` (`raise_closed_attempt`) listener is absent, so closed-command attempt fences and hosted prepared-edit guards raise raw `IntegrityError` (HTTP 500) instead of `ClosedCommandError` (HTTP 409 `submission_closed`) or `PreparedEditRequired`.
4. String interpolation `f"sqlite:///{self.database}"` breaks if the workspace path contains `#` or `?` and fails `engine.url == scope[0]` in `workspace_mutation_scope` if `self.database` is non-canonical, silently bypassing hosted mutation admission guards.
Impact:
Maintenance mutations lose SQLite foreign-key integrity, immediate write-lock reservation, attempt-fence/prepared-edit error handling, and potentially hosted mutation admission gating.
Fix:
Initialize `self.engine = create_sqlite_engine(database)` once in `SQLiteMaintenanceUnitOfWork.__init__()` and reuse it in `write()` and `read()` (matching every other SQLite unit of work).

Phase 2: Cross-Boundary Synthesis & Recommended Remediation Sequence
================================================================================

Cross-boundary patterns observed across Waves 1-9:
1. Business-date timezone consistency (Findings 7, 13, 15):
   Finance, Owner Accounting, Owner Management, and Operator consistently use stored Property `ZoneInfo` or explicit `asOf`, whereas Leases, Portfolio, Tenants, Inspections, Vendors, and Web `leasing.tsx` still fall back to host OS `date.today()` or browser UTC `new Date().toISOString().slice(0, 10)`. On UTC-hosted Pilot 0, this breaks same-day lease execution/voiding after 4-5 PM US Pacific.
2. SQLite engine/connection discipline (Findings 4, 9, 12):
   Almost all modules use `create_sqlite_engine()` and `closing(sqlite3.connect(...))`, except `SQLiteMaintenanceUnitOfWork` (raw `create_engine()`), `BackupService._audit*` (missing `closing()`), and `SQLiteInspectionUnitOfWork.write()` (over-broad `OperationalError -> 409`).
3. Read/verification query budgets (Findings 1, 2, 8, 11):
   `GET /health` and `GET /api/workspace` re-run full 18-module schema+data validation per request; `FileStorageVerificationService.verify()` re-verifies all files on every S3 continuation page; `SQLiteInspectionUnitOfWork._report_view()` has 3-level nested N+1; `PrepaidCheckService.list()` runs 4-5 queries per check.

Recommended remediation order:
- Batch 1 (P1 correctness & data integrity — fix first):
  Findings 6 (same-day deposit void guard), 12 (Maintenance `create_sqlite_engine`), 7 + 13 + 15 (Property-timezone business dates across backend & `leasing.tsx`), plus Finding 18 regression tests.
- Batch 2 (P2 reliability & query budgets):
  Findings 1 (`/health` & `/api/workspace`), 2 (S3 verify continuation), 3 (`FileService.upload` replay rollback), 4 (`BackupService` `closing()`), 8 (Inspection N+1), 9 (Inspection `OperationalError`), 11 (PrepaidCheck N+1).
- Batch 3 (P3 hygiene & polish):
  Findings 5 (`file_too_large` code), 10 (5 cross-module ORM imports), 14 (`BackupProxyServer` exception log), 16 (`HostedSettings` `checkHostedResponse`), 17 (`hosted_package.py` PEM check & `--output` resolve).
