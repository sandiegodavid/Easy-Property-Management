SPECIFICATION — Hosted identity and session revocation

1. [P2] Fence the assertion presented during current-device logout.
Status: resolved — 2026-10-25
File: application/apps/server/app/modules/hosted_access/infrastructure/session_store.py:302-310
Related: application/apps/server/app/modules/hosted_access/application/service.py:107-108; application/apps/server/app/modules/hosted_access/api/router.py:77

revoke() blocks only the assertion fingerprint stored when the application session was created. authenticate() permits a different valid assertion for the same subject, but logout() does not receive that current assertion. If assertion A creates the application session and Cloudflare subsequently supplies refreshed assertion B, logging out with B revokes the application session and blocks A; an immediate POST /api/hosted/session using the already-issued B still succeeds. The operator can therefore start another application session without the fresh identity sign-in promised by the current-device logout contract in docs/hosting/design/HOSTED_DEMO_DESIGN.md, section 2.

Pass the current verified assertion fingerprint and expiry into logout and persist its bootstrap block atomically with session revocation. Preserve the original assertion block and other existing device sessions. Add a regression test with different bootstrap and logout assertions.

Validation: reproduced using the real SQLite session store and application service: create session with A, authenticate/logout with B, then begin_session(B) succeeds.

Resolution: logout receives the current verified identity and atomically blocks both the original and presented assertion fingerprints until their respective expiries. Regression coverage rejects bootstrap with either assertion, preserves other devices, and proves rollback if the current-assertion block fails. The hosted browser session test refreshes the assertion before logout and confirms immediate bootstrap returns 403.

SPECIFICATION — Saved-form recovery and edit authority

2. [P2] Allow original-key recovery after a committed response is lost and edit authority expires.
Status: resolved — 2026-10-25
File: application/apps/web/src/shared/recovery.ts:133-135
Related: application/apps/web/src/shared/recovery.ts:191-196 and 293-300; application/apps/server/app/modules/hosted_access/application/draft_leases.py:30-36

When a recovery save or attempt preparation commits but its response is lost, the controller retains pendingSave/pendingPrepare while its acknowledged record revision remains old. After session reauthentication or loss of the edit lease, claimEditing(), including explicit takeover, sends that old revision and receives hosted_draft_revision_conflict. The offered Review latest saved form action cannot resolve this because reviewLatest() rejects while either pending request exists. The retained editor is stuck: it cannot acquire authority to retry the original key and cannot review current saved metadata to recover. This violates the interrupted-response/original-key recovery requirements in docs/hosting/design/HOSTED_DEMO_DESIGN.md, sections 5 and 6.

Provide an authorized recovery path that obtains current saved metadata and reacquires edit authority while retaining the immutable pending payload and original operation key. Do not rebase the pending operation or create a replacement key. Add browser coverage for committed-but-lost autosave and preparation responses followed by lease expiry or session expiry and explicit reauthentication.

Validation: an isolated Node probe loaded recovery.ts from e35de731. A save advanced server revision 0 to 1 and returned an unknown outcome. After lease pause, takeover still sent revision 0 and failed; reviewing revision 1 failed with Reconcile this record before reuse.

Resolution: explicit edit claims read the current durable revision when an original save/preparation remains pending, without replacing its payload, operation key or expected operation revision. Metadata review preserves pending operations; successful reclamation makes a lease-rejected pending save retryable. Four real hosted browser cases cover committed-but-lost saves/preparations followed by session reauthentication or lease loss/takeover; every retry retains identical request bytes. Existing stale-editor and cross-workspace isolation checks also pass.
