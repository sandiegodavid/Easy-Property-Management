# Hosted demo administration and additional operators

Design — review recommendations accepted October 27, 2026. No implementation or deployment is performed by this document. Existing two-operator qualification remains in force until the extension is accepted and tested.

## Can the current Google demo add a third operator?

Yes, as another isolated demo instance on the same VM, subject to capacity qualification. Each operator keeps a separate portfolio, service, Unix identity, access database, hostname and bounded private storage. Slice 8 replaces individual loop-image filesystems with private directories and project quotas on a shared host filesystem. This extends the current hosted-demo topology; it does not put several operators into one business workspace or deliver SaaS collaboration.

The application configuration has no global two-operator maximum: `HostedDeployment` pins one `operator_id`, `allowed_email` and `workspace_id` per process. The templated `epm-hosted@.service` can name additional instances. Provisioning remains manual; Slice 1 implements inventory-based private tooling in the repository, with live adoption/qualification still separate. Simply adding another email to A's Access application would not create C's workspace or authority.

## Recommended scope

Build a small, separate host administration console for the deployment owner. Start by qualifying a third isolated operator; increase the recorded qualified limit only after repeating the load and recovery gates. Provisioned or suspended portfolios still consume disk even when their services are stopped.

Include operator creation, verified enrollment approval, invitation preparation, expiration renewal, immediate disablement, session revocation, service status, recovery status and resumable failed operations. Include all Admin UI and backend work in this delivery. Continue to use existing release/backup/reset services rather than inventing a second business-record or recovery implementation.

Keep destructive reset, data restore, release installation, VM/root-disk resizing and data deletion in the existing private runbooks. Upgrading an existing operator to an already installed release is an approved Admin UI extension, specified below; until that extension is implemented and qualified, deployment remains a private-runbook operation. Slice 8 adds bounded per-operator storage provisioning/changes and operator upgrade requests, as specified below. The UI can show private-operation status and mark an operation as requiring a private administrator step. No automatic email sending, billing, shared-workspace roles, arbitrary remote commands, real customer portfolios or provider credentials in the business app.

The accepted [PAY-001 tenant-payment design](../../active/PAY-001_DESIGN.md) is a separate hosted product track. Do not add tenant invitations, premium billing or real-money permissions to this synthetic demo console. The delivered 250 MiB **whole workspace volume**, Slice 8's selectable **usable workspace allowance backed by project quotas**, and PAY-001's proposed 250 MB **attachment allowance** are different measures. Slice 8 supersedes the demo's fixed-volume provisioning design once implemented and qualified; it does not revise the production free/premium offer. A production provisioning profile must separately reserve database, audit, access, temporary and recovery storage before reusing any Admin machinery. Synthetic and production inventories/configurations must have explicit deployment-kind boundaries; this console can create only synthetic demo instances.

This proposal extends the bounded experiment under SAAS-001/SEC-001/SEC-002; it does not change their completion status or the local MVP's no-login behavior. Do not silently turn the current two-instance acceptance evidence into an N-instance claim.

## Administrator workflow

### 1. Open administration

The deployment owner runs one documented launcher on their computer. It opens an IAP SSH forward to a separate loopback-only Admin service on the VM, then opens its local browser URL. The console is not exposed through the public operator tunnel and does not appear in operator Settings.

The launcher obtains a short-lived single-use bootstrap credential through the authenticated SSH channel. Paste it into the console sign-in form; never place it in a URL, command-line argument, browser storage or log. Bind the issued session to the pre-provisioned administrator identity. An IAP/SSH connection is transport access, not permission for arbitrary local browser requests. The console requires its own session and CSRF protection.

For the initial single administrator, provision identity and recovery CLI access privately during installation. Additional administrator accounts and public Internet Admin access are separate scope. The console cannot grant itself access or manage Google IAM.

### 2. Review the overview

Show active/qualified operator count, available memory, disk reservations, remaining Access seats, tunnel status and oldest verified recovery point. Each has an observation time and available/unknown/stale state.

The primary button is **Add operator**. If blocked, show the specific reason and remediation, such as “Three operators have not passed the capacity test” or “Reserve space for this workspace and its recovery copies.” Permit saving an operator setup draft while capacity is unresolved, but do not allocate ordinary operator resources or invite anyone. Link the capacity blocker to **Qualification plan**, which shows the separate private test procedure below and its evidence/status. Only an explicit, bounded qualification reservation may create test instances above the ordinary qualified ceiling; it does not raise that ceiling or admit invitees.

### 3. Add an operator

Use three short steps, retaining an acknowledged setup draft between steps:

1. **Operator:** display name, exact sign-in email, optional non-secret reference code and support contact. Explain that the code is a label, not a password. Each operator signs in with their own approved email and may use several devices. Default to a fresh synthetic portfolio; offer an empty synthetic workspace. Do not offer cloning another operator's edited database.
2. **Demo:** select an already installed, qualified release and synthetic template version; choose start and expiry within the existing fourteen-day window. Slice 8 adds a **Workspace storage** dropdown: **50 MB (default)**, **200 MB**, **1 GB**, using the usable allowance defined below. Show the assigned hostname, storage/file limits, capability profile and expected backup policy. Hostname, UUIDs, Unix user, paths and ports are generated from host inventory, not editable shell/path inputs. Read/write demo is the normal profile; read-only remains an explicit supported alternative.
3. **Review:** summarize recipient, isolation, dates, reservations and steps. **Create isolated demo** starts one durable operation. Existing A/B instances are not restarted or rebound.

Reject accidental duplicate active email assignments by default and offer **Open existing operator**. A deliberate second workspace for the same email is outside the initial workflow. Compare according to the configured identity policy; never strip plus-addressing or provider-specific dots to infer an identity.

Closing the browser does not cancel a committed provisioning job. The overview shows its progress and links back to the operation result.

### 4. Provision without granting business access

The job reserves the instance key, exact hostname, port, storage and resource profile; provisions the non-login Unix account, private directories, bounded storage, private temporary storage, root-owned configurations and per-instance access database; creates and validates fresh workspace identities; then starts its single writer. The delivered baseline uses a fully allocated 250 MiB image/mount. Slice 8 instead allocates private directories with inherited project IDs and verified hard quotas on one shared filesystem, with no per-operator image, mount or format operation. A selected 50 MB allowance must fit the verified seeded or empty workspace before onboarding can proceed.

Configure an exact-host Cloudflare Access application/audience and exact-email policy before publishing the tunnel route/DNS. A route must never expose an origin that has no matching Access protection. Keep the tunnel catch-all deny rule. Verify enforcement, host/audience/workspace binding and service readiness, not just DNS resolution.

The first release uses verified manual Cloudflare setup. Pause at **Administrator setup required**, give precise Dashboard instructions and expected non-secret identifiers, then independently verify the observed application, policy, audience and route. Cloudflare tokens and tunnel credentials never pass through the browser. Automated provider mutation is deferred until credential scope and tunnel-management mode qualification; manual completion is not a checkbox assertion.

After resource checks, show **Scheduled · Starts [time]** before the enabled window, or **Waiting for first sign-in** once it opens, not **Active**. Before the start time, do not promise enrollment or business access; retain the existing date checks. Prepare a copyable invitation containing the assigned URL, exact sign-in email, start and expiry with a named time zone and UTC offset, synthetic-data restriction and support contact. The administrator sends it manually. **Copy invitation** is not delivery confirmation. A pre-enrollment recovery point protects the fresh data; approved-binding recovery must be refreshed after enrollment.

Use these instructions in the invitation, populated from the current deployment window:

> Your demo opens [start date/time, zone, UTC offset] and expires [expiry date/time, zone, UTC offset]. Before it opens, the link may show that access has not started; return at the start time. Then open [assigned URL], sign in with [exact email] using Cloudflare's email PIN, and select **Continue to workspace** to request approval. A pending-approval screen is expected on first use. Contact [support] if needed; do not repeatedly request new PINs to resolve pending approval. After the administrator confirms setup is complete and access is ready, return to the same link and select **Continue to workspace** again. Renew sign-in if prompted. Use synthetic data only.

### 5. Approve the verified enrollment

The operator opens the link and completes Cloudflare sign-in. Existing EPM bootstrap creates a pending subject without returning business data. The Admin detail screen then shows the verified issuer, email, subject reference, received time and intended operator/workspace binding.

The administrator checks the intended person and selects **Approve identity**. Bind approval to the exact current pending enrollment and instance revision; never approve from a typed email alone. Validate current dates, resource qualification and healthy runtime again. Persist the approved identity while keeping business-session issuance fenced. This is a new source-owned operation: the existing `activate()` method cannot implement identity-only approval because it also enables access.

Show **Identity approved · Recovery verification pending · Business access blocked** until an encrypted approved-binding reference is published/read back and new-instance acceptance is verified. The operator's pending screen explains that setup is still underway. Final ready-to-use instructions become available only after **Complete onboarding and enable access** succeeds. Existing sessions, token hashes, CSRF material and draft leases never enter recovery bundles.

### Recovery-pending handoff and completion

In this state the primary action is **Verify onboarding recovery**. It opens a persistent checklist linked to the instance and operation, not a transient modal. Show the exact instance key, workspace UUID, current binding revision, approved-subject reference and pinned configuration digest; the support-facing summary uses safe references rather than credentials. Link directly to [daily manual recovery points](../operations/HOSTED_DEMO_OPERATIONS.md#daily-manual-recovery-points) and [administrator recovery bundles](../operations/HOSTED_DEMO_OPERATIONS.md#administrator-recovery-bundle-and-host-loss).

The checklist presents the private terminal launcher with the server-assigned instance and handoff IDs as fixed arguments. Its implementation is part of the recovery tooling slice: it loads the registered paths/configuration itself and runs the existing backup, publication and reference validators as the appropriate owner. No passphrase is entered into the browser. It must produce a protected verification report even when a step fails; a printed “success” or pasted object name is not evidence. Report generation and registration are a new adapter over the existing private recovery procedures, not an already available command.

Required evidence is a validated encrypted business archive, independent off-host read-back/decryption and workspace identity validation, a successful isolated restore drill for this new workspace, and an encrypted approved-binding reference independently read back/decrypted and compared with the current binding. Record point IDs, digests, source snapshot marker, completed-at times, verifier/release identity, restore result and policy-age checks. Do not put decrypted data or secrets in the report. A binding revision changes when the operator/workspace/approved identity or pinned deployment configuration changes; ordinary session issuance does not change it. The approved-binding reference must be captured after that binding was approved.

The private helper registers the report through the authenticated local broker into a protected evidence registry. Bind it to the handoff ID, instance/workspace UUIDs, binding revision and configuration digest; prevent ordinary browser or operator callers from publishing verification assertions. The browser's **Check verification** sends only the handoff ID and expected instance revision. The backend reads the registered report, verifies provenance and required successful checks, compares all current identities/digests, and checks recovery age against policy. It returns missing, failed, stale or verified evidence with specific next steps. Arbitrary browser-provided report paths and manually checked boxes cannot satisfy verification.

Reloading or reconnecting restores the same checklist and registered evidence. If the binding changes during the terminal work or verification, retain the report as history, mark it stale for onboarding and require a new binding reference/check. Do not mark the operator complete automatically. When recovery evidence and new-instance acceptance are current, enable **Complete onboarding and enable access**. This explicit audited action includes the verified evidence ID, acceptance record ID and expected instance revision; it rechecks both records, the current binding, dates and instance/admin authority fences through the source-owned access command. The access-store receipt atomically records activation and its audit; the control-plane completion references that receipt and reconciles a lost response rather than claiming a distributed transaction. A conflict or stale evidence preserves recovery-pending state. A successful action records the onboarding result and changes lifecycle to **Active · Onboarding complete**, enabling the approved subject to obtain a fresh eligible business session. It does not issue or renew a session itself. Offer **Copy ready-to-use instructions**: “Your demo is ready. Return to [assigned URL], sign in with [exact email] if prompted, and select Continue to workspace. Access expires [time, zone, UTC offset].” Copying is not delivery confirmation. Completion is idempotent; new access/binding changes require their own verification and cannot reuse stale completion evidence.

Pre-activation acceptance verifies workspace integrity, isolation/configuration, protected ingress, pending-enrollment behavior and recovery using private tooling and qualified release evidence. It must not require the new operator to access business records before completion. After activation, record a separate operator sign-in/smoke check; a failure triggers containment and remediation, not fabricated pre-activation evidence.

### Operational recovery after onboarding

Onboarding evidence is a point-in-time result, not a permanent green recovery badge. Warn at 20 hours and mark recovery overdue at 24 hours since the last verified off-host recovery point. Block new onboarding completion on stale or overdue required evidence; do not automatically disable existing operators for a late backup. Create an acknowledged administrator remediation task. Each instance has a recovery policy with last attempted/successful backup and publication, latest verified restore drill and next due action. A changed binding/configuration invalidates binding evidence immediately; a later business write does not invalidate the fact that an older archive was verified, but exposes the archive's snapshot marker/time and potential uncovered changes. Failed or overdue recovery appears in Needs attention with a private-runbook action. Do not claim automatic backup execution while passphrase entry is manual.

**Repository implementation (Slice 6):** the private recovery verifier and protected report registry now complement the existing [binding bundle helper](../../../application/apps/server/app/modules/hosted_access/infrastructure/recovery_bundle.py). The worker evaluates recovery age independently of console visits; missing evidence remains Unknown and retained recovery history stays readable when the writer is stopped. See the [lifecycle runbook](../operations/HOSTED_ADMIN_LIFECYCLE.md) for manual verification, attention, completion and qualification boundaries.

### 6. Maintain access

| Control | Meaning / confirmation |
| --- | --- |
| Copy sign-in instructions | Copy the existing assigned URL and instructions; does not grant or renew access |
| Approve pending enrollment | Record exact verified identity only; business access stays fenced until recovery/completion gates pass |
| Extend demo | Explicit new window within the existing maximum fourteen-day duration, expiry preview, configuration validation and recorded cutover; never silently extend on sign-in |
| Revoke all sessions | Keep the assignment; durably revoke current sessions and require fresh eligible identity proof |
| Disable access | Immediately fence app authority, revoke sessions/leases, then remove edge allowance/revoke provider access; retain records and recovery points |
| Enable access | Requires an explicit healthy/qualified/unexpired instance, reviewed approved binding, current recovery/completion evidence and fresh proof; never undo a pending disable automatically |
| Change sign-in email | Private assisted rebind: disable, stage exact new policy/configuration, receive verified replacement enrollment, explicitly rebind/activate; old identity remains denied |
| View operation | Status, safe error, timestamps, completed and next steps; **Resume** retries the same operation |

Disable/revoke must work if the workspace is full, corrupt, expired or its writer is stopped. If the access store cannot be fenced, stop and verify the owning service and block its ingress; show **Containment pending** until denial is observed. Never report success based only on an upstream API acknowledgement. A disabled operator can still own retained data; **Disable** is not **Delete**.

Email replacement and expiry renewal need coordinated config/runtime changes because the current deployment object is immutable. For renewal, fence/drain that instance, atomically publish validated config, restart with its existing workspace, verify effective dates and require fresh sign-in before activation. Record old/new configurations and resume state; do not restart all operators. If failure occurs, leave the target fenced for explicit recovery. Where an email change needs private assistance, show this honestly rather than presenting a nonfunctional button.

### Renewal and identity replacement contracts

**Current gap:** [deployment validation](../../../application/apps/server/app/modules/hosted_access/application/configuration.py) limits the entire `enabled_at`–`expires_at` interval to fourteen days. Extending only the expiry of an existing fourteen-day window fails validation. Renew means confirm a new positive window of at most fourteen days with an explicit new start, preserve the original onboarding date separately, then fence/reconfigure/restart only that instance. Show any gap or overlap, invalidate old sessions and require fresh proof. Record immutable window history, original onboarding date, renewal count and retained resource cost. Explicit reasoned renewals have no cumulative lifetime maximum for this controlled pilot; each window remains at most fourteen days. No automatic renewal; expired data remains retained until private retirement.

The [current rebind operation](../../../application/apps/server/app/modules/hosted_access/infrastructure/session_store.py) changes the subject only; it is not an email/configuration replacement command. Implement a typed replacement handoff that keeps old authority disabled while a new validated configuration/access binding receives replacement enrollment. Preserve old access audit history without copying live sessions into the replacement store. The new subject must be verified under the new exact email/issuer/audience; merely editing `allowed_email` and calling `rebind` is insufficient. Expose Pending replacement and explicit recovery steps if any cutover fails.

## Upgrade an operator to an installed release

This approved design extension is not a claim of implementation or live qualification. Add **Upgrade release** to the operator detail **Runtime** section beside the current release. Preserve the workspace, approved identity, hostname, permissions and enrollment window. Deliver the backend and usable Admin workflow together; installing release artifacts remains private administration.

### Choose the release and check readiness

Open a dedicated **Upgrade operator** page showing the operator/workspace, current release, installed target releases, installation dates, available release notes, compatibility and qualification status. Only eligible targets are selectable. Explain unavailable choices inline, such as “Workspace format unsupported” or “Release qualification required.” Buttons: **Cancel** and **Check readiness**.

Check readiness asynchronously while the operator continues working: workspace/access-store compatibility, target artifact integrity and applicable qualification, service/configuration/inventory consistency, backup storage and recovery-tool readiness, and conflicting maintenance. Show specific remedies and **Check again** for blockers; provide no bypass. These checks neither create the final recovery point nor guarantee unchanged conditions. Repeat critical checks at execution.

### Confirm the interruption

Show current → target release, affected operator, recovery plan and this explanation: “Access will pause while the upgrade runs. Ask the operator to save unfinished work before continuing. Valid sessions can remain signed in; open tabs must reload before continuing.” Require action-bound administrator reauthentication and confirmation of an agreed maintenance window. Buttons: **Back** and **Start upgrade**. Explain that a failed upgrade can leave access paused until recovery completes; do not promise downtime without measured evidence.

### Session handling and browser continuity

On the confirmation screen offer **Keep valid sessions** (default for a compatible routine release) and **Require sign-in again**. Target release compatibility/security evidence determines whether preservation is supported; unknown compatibility blocks preservation. Authentication/session-format changes, authorization or identity-binding changes, security remediation requiring invalidation, and data restoration require revocation. Explain a mandatory selection inline and prevent overriding it. Persist the reviewed choice and its eligibility evidence in the operation; recheck eligibility before interruption.

A mandatory source-owned maintenance gate blocks all operator business reads/writes, new session issuance and background business writers while the upgrade runs, independently of session validity. Existing `disable` advances session generation and therefore cannot implement a session-preserving pause. Add an explicit maintenance pause/resume contract with operation ownership, expected revisions, durable audit and idempotent receipts. It must survive process restarts, coexist with private maintenance, and remain closed through verification, failure and rollback until explicit acceptance. Private readiness checks need narrowly scoped tooling access while ordinary operator requests remain blocked.

Preserved sessions retain their original expiry, identity and authorization checks. Never revive expired/revoked sessions or overwrite an intervening disable, identity change or all-device sign-out. Acceptance removes only this operation's maintenance gate; it does not grant authority removed elsewhere. A later requirement to revoke must be recorded and surfaced explicitly before access resumes.

Open tabs show “Upgrade in progress” during maintenance. After acceptance they show “A new version is ready—reload to continue.” Use a release identity check and a server-enforced compatibility gate so stale clients cannot submit business mutations before reloading. Revocation alone does not refresh browser code. Preserve unfinished form data where compatible; if incompatible, explain what needs review rather than silently dropping or submitting it. Reconcile uncertain pre-upgrade submissions by their original identifiers before allowing retries. Sessions that remain valid continue after reload without additional sign-in; other sessions follow the normal sign-in workflow.

### Execute and show durable progress

Create the durable operation before any effect, then display these checkpoints:

1. Reserve the instance and revalidate its current state.
2. Enter the maintenance gate, revoke sessions only when selected or required, drain in-flight work to a verified quiescent state and stop the service.
3. Create and verify the recovery point.
4. Validate the target against the stopped workspace.
5. Switch the instance to the target release.
6. Start the service with the maintenance gate still closed.
7. Verify runtime, workspace integrity and protected routing.
8. Await administrator acceptance.

The recovery point includes the business archive and binding/configuration evidence required for recovery, with independent off-host verification under the existing recovery policy. Credentials come from protected host configuration. Missing credentials produce **Private administrator step required**, never a browser passphrase field. A release/configuration change requires evidence applicable to the resulting binding before access can be restored; the pre-upgrade backup alone does not prove target readiness.

Closing the page does not cancel execution. Reopening the operator shows **Upgrade in progress → View progress**. Disable conflicting mutations while retaining emergency containment. Cancellation is available before access is paused; afterward expose controlled recovery actions instead of abruptly terminating the worker.

### Accept and restore access

When verification succeeds, show “The new release is running. Verification passed. Operator access remains paused,” the verification summary and recovery reference. Offer **Accept upgrade and restore access**, **Roll back** and **View details**.

Before reopening access, recheck the binding, current recovery evidence, enrollment validity, session-handling eligibility and any intervening disable/revoke action. Acceptance must not override an expired enrollment, prior disabled state or subsequent containment decision. For those cases offer **Accept upgrade and keep access disabled** with the reason. Record completion and operator sign-in verification separately; operator business access is not a prerequisite for pre-activation checks.

### Failure, resume and rollback

| Situation | Admin behavior |
| --- | --- |
| Readiness fails before interruption | Explain the remedy; the operator continues on the current release. |
| Failure after access is paused | Show the failed step, actual service/access state and specific next action. |
| Browser loses connection | Show “Checking operation status” and look up the original operation; do not submit a new upgrade. |
| Recoverable interruption | **Resume upgrade** continues from verified checkpoints. |
| Target validation/startup/health fails | Offer **Roll back** when its prerequisites pass. |
| State cannot be established safely | Show **Private intervention required**, an operation reference and precise instructions. |

Rollback first validates that the previous release can still read the workspace. It must not silently restore an older backup and discard records. A required data restore is a separate explicit recovery operation. Preserve the previous release and recovery evidence until retention policy and release-protection checks permit cleanup.

### Backend and command contracts

Extend the existing operation journal and privileged broker with typed readiness, upgrade, acceptance, resume and rollback commands. Extract deployment steps into a noninteractive service shared with the private CLI; do not execute the interactive shell wizard from an HTTP request. Existing source-owned access receipts, maintenance reconciliation and audit remain authoritative.

Persist original/target release identities and artifact digests, instance and binding revisions, prior access state, selected/required session handling and eligibility evidence, maintenance-gate ownership, recovery references, checkpoints and final result. Submission uses an idempotency key; state-changing decisions use expected revisions. Resume verifies actual service/configuration state before repeating an effect. Reconcile the registered release and observed runtime as part of completion so the UI cannot report success over an unresolved inventory discrepancy.

Use brief host-wide locking for admission/shared configuration changes and a durable reservation for the affected instance. Long backups and verification must not block emergency disablement of another operator. This requires coordinating with existing private-maintenance locking, not bypassing it. The broker resolves paths, commands and credentials; the UI receives sanitized identifiers and status. Upgrade one instance at a time initially.

### Bulk operator upgrades — Slice 7 extension

Approved scope addition November 1, 2026: let the Admin select several registered synthetic operators and manage their release upgrades from one durable batch. This extension is **repository delivered** with the Admin workflow and focused validation recorded in the [upgrade runbook](../operations/HOSTED_ADMIN_UPGRADES.md). It is not live-qualified or deployed. The delivered single-operator workflow remains available. Bulk selection does not authorize parallel downtime, new release installation, additional operators or a higher qualified ceiling. Execute at most one operator upgrade or rollback on the host at a time, using the same source-owned maintenance, recovery, session, authority and acceptance guarantees above.

#### Select, check and review

Add **Upgrade selected operators** to the Admin operator directory. Use labeled row checkboxes, a selected count and **Clear selection**; enable the action only with a selection. Selection is explicit across bounded directory pages: **Select this page** selects only visible rows, never hidden or future search matches. Preserve the selected references when filters change and show every selected operator in the review. The initial batch limit is 50 distinct registered operators; enforce it before admission and explain it in the UI. This request-size limit does not establish hosting capacity.

Open a dedicated **Upgrade operators** page. Show the selected names, current releases and access states, one installed target release, the proposed execution order and per-operator session handling. Default the order to operator name plus stable inventory reference; allow the Admin to move rows before review. Exclude no operator silently. Already-current operators, conflicting operations, unknown inventory, unsupported formats, stale qualification and missing recovery prerequisites appear as explicit blockers. The Admin can remove a row or fix its blocker and select **Check readiness again**. No selected operator is interrupted by these checks.

Run bounded asynchronous readiness checks for each member against the same target artifact. Qualification must match each operator's profile and the actual retained host count; checks for one member do not establish readiness for another. Show per-member observation times and remedies. Keep valid sessions by default only where qualified; require sign-in again for each member that cannot preserve sessions. Readiness must pass for every included member before **Review batch** is available. Recheck critical facts immediately before each member starts, because earlier readiness can become stale while the batch waits.

The confirmation shows the exact membership/order, source and target releases, session decisions, recovery requirements and agreed maintenance window. Explain: “Operators are upgraded one at a time. Each stays paused until you accept its verified release. A failure stops the remaining queue.” Require confirmation and fresh action-bound authorization for **Start batch**. This authorizes only the reviewed forward-upgrade plan; it does not authorize later acceptance, rollback, membership changes or a data restore. A member may start only within the confirmed maintenance window; if it closes, leave unstarted members queued for an explicitly reviewed new window. Do not infer permission from a current browser session or silently extend the window.

#### Progress, acceptance and queue controls

After admission, show a dedicated **Batch upgrade progress** page with target release, completed/selected count, current operator, maintenance window, per-member status and links to each original operation. Include **Queued**, **Checking readiness**, **Upgrading**, **Awaiting acceptance**, **Accepted — access restored**, **Accepted — access disabled**, **Blocked**, **Failed** and **Skipped**. Progress counts describe verified outcomes; missing status never becomes success. Preserve the exact selection and command key across reload or a lost response. GET, reconnect and polling only look up status; they never create or retry upgrades.

Reuse the existing single-operator checkpoint and recovery view for the current member. Unstarted members continue serving normally. After runtime and recovery verification, keep the current member's gate closed and offer **Accept and continue**, **Accept with access disabled and continue**, **Roll back this operator** and **View details**. Each acceptance requires a new action-bound credential for that exact child operation, revision and access choice. **Accept and continue** never accepts unverified or future members. Record the source receipt and reconcile the child's outcome before starting the next member. Sign-in verification remains a separate observation, not a prerequisite to accepting a deliberately disabled operator.

Offer **Pause after this operator** and **Cancel remaining operators** on the batch page. These decisions are revision-checked and durably stop new dispatch before acknowledging success. They do not abort a running backup or remove an existing maintenance gate. If a member has already started, its normal acceptance/recovery controls remain available; cancellation marks only unstarted members skipped with the cancellation reason. A paused batch needs explicit **Review and resume batch**, a fresh applicable window/readiness review and action-bound authorization. #### Failure and isolation

Already accepted members retain their outcomes; there is no all-or-nothing rollback across workspaces. Automatic retry, acceptance and rollback are not allowed. Resume the original child or explicitly roll back that operator through the existing workflow, preserving the current workspace bytes. A rollback requires its own authorization and explicit acceptance. After a rollback or failed-member recovery, leave the batch paused for review rather than advancing automatically.

Allow **Skip this operator and continue** only after explicit review, reason and authorization. For a started member, first establish a safe contained or accepted outcome and release its active worker/maintenance reservation through existing reconciliation. Retain its failed/rolled-back result and any continuing access pause; skipping never clears a source gate or converts that result to an upgrade success. Recheck remaining members before resuming. Finish as **Completed** only when every selected member reached its intended accepted target; otherwise show **Finished with skipped or failed operators**, with separate counts and follow-up links.

Emergency Disable/revoke remains available for any operator. A source fence, changed binding, disabled access or expired enrollment always wins over the batch's earlier plan. Admin generation revocation fences both coordinator and children; restoring Admin identity does not restart the queue. Control-store restoration retains the plan, child links, evidence and receipts but fences dispatch until explicit reauthorization and reconciliation. Short coordinator/admission transactions must not hold host or database locks over backup, provider or source calls. Competing single upgrades, other batches and private maintenance use the existing host execution reservation; no second child starts while another upgrade or rollback owns it.

Reject duplicate operators, unknown inventory, over-limit selection and changed-payload reuse of an idempotency key. Never resolve membership later from a saved filter.

Retain append-only control decisions, coordinator revision, one original forward-child ID per member, any linked rollback operations, recovery references and original results. Use a worker claim plus transactional revision checks to prevent two coordinators advancing the same queue. Persist pause/cancel decisions before racing child admission, so exactly one outcome wins: the member is already admitted and shown as current, or it remains unstarted. Reserve only the current child's execution resources; do not put all queued operators into maintenance. Reconcile the original child's source receipt before advancing after a lost response. Parent progress reads project retained control-plane facts with set-based queries and bounded member pages (default 10, maximum 50); do not synchronously open every workspace or call providers. Extend the current greenfield control schema, audit and encrypted control recovery with these parent/member/decision links and validation of order, membership uniqueness, target/session bindings, legal transitions and one active child. Do not copy usable grants, sessions or provider credentials into recovery artifacts. ## Shared filesystem, project quotas and storage requests — Slice 8

Approved design addition November 1, 2026; **8A is locally qualified and repository delivered; 8B–8H remain planned and nothing is deployed**. ### One filesystem, private operator directories

Use one qualified shared EPM data filesystem, initially ext4 with project-quota accounting and enforcement enabled. Reuse the existing host filesystem if it qualifies; a separate shared data filesystem is an installation option only when needed. Operators share the Linux OS/kernel and filesystem, but retain separate non-login Unix identities, private directory trees, business databases, access stores and services. A project quota limits resource consumption; Unix permissions and the service sandbox enforce read/write isolation. No operator-specific partition, disk image, loop device or mount is created.

The privileged broker assigns unique nonzero project IDs from the protected inventory, sets project inheritance on each tree and verifies actual descendants. Keep IDs reserved while data, open files, recovery work or uncertain effects remain; never derive them from email or reuse them on retirement without verified cleanup. Resolve paths through registered identities, not browser input. Restore/copy creates files under the destination project and verifies attribution; changing the top directory's ID is not a recursive conversion. Cross-operator hard links, shared writable files and cross-project renames are unsupported. Deduplication may share evidence within one workspace only.

Use a **workspace project** for each operator's persistent database/evidence tree, and a separate **scratch project** for that operator's private TMPDIR and bounded temporary processing. These are directories on the same filesystem, not additional filesystems. Give the external per-instance access/control store its own bounded control allocation so a full workspace cannot prevent sign-in, upgrade requests or containment; cap control/log storage independently. Backups/recovery staging have a separately reserved administrative budget and are inaccessible to operator identities. All writable paths, including runtime temporary paths and deleted-but-open files, must remain within an accounted budget. System service private `/tmp` settings alone are not proof of quota attribution.

Host installation must verify kernel/e2fsprogs support, filesystem identity/features, project-quota enforcement, inherited project IDs and both block/inode limits with a real unprivileged write test. Do not infer readiness from mount-option text. Enabling features on an existing root filesystem may require offline maintenance/reboot: that is a separately reviewed private installation procedure, never an effect of **Add operator**. No automatic fallback to application-only limits, loop images, reformatting or VM resizing. Existing services stay on their registered backend until their own controlled transition is accepted.

This removes per-operator filesystem provisioning and resizing, but all operators now share filesystem failure, I/O contention and global free-space/inode pressure. Keep existing service CPU/memory/I/O controls and host monitoring. Project quotas do not isolate I/O latency, reserve metadata or make recovery independent of the shared filesystem. A shared enforcement failure fences affected growth and raises one host-level Admin incident; do not present every operator as independently healthy because their services are running.

The service must be unable to change project IDs or inheritance, disable quotas, mount another filesystem or write to unbudgeted paths. Dropping `CAP_SYS_ADMIN` and hiding the `chattr` executable are insufficient evidence: inode-owner file-attribute interfaces can allow project changes on some kernels. Qualify a kernel-enforced sandbox that blocks the applicable project/attribute mutation ioctls (including compatibility interfaces) or an equivalently verified isolation mechanism, without granting broad quota capabilities to the application. Attempt these escapes directly as the actual service identity before accepting isolation. Failure blocks this backend's qualification. Technical evidence and primary sources: [project-quota research](../../research/HOSTED_PROJECT_QUOTA_RESEARCH.md).

Primary action follows the state: **Resume setup**, **Copy invitation**, **Review enrollment**, **Verify onboarding recovery**, **Complete onboarding and enable access**, or **Extend demo**. Offer **Copy ready-to-use instructions** only after completion enables access. Identity approval alone never enables business access. Secondary menu contains revoke/disable. Destructive controls are visually separated and require a plain-language consequence plus reason.

Sections:

- **Access:** intended email, verified binding, activation/expiry, supported capability profile and valid app-session count. No “online now” claim: the existing authorization path deliberately does not write last-seen per request. Never return session/lease/assertion hashes.
- **Runtime and capacity:** effective release/checksum, service and storage-backend checks, reserved/measured memory and disk with timestamps; exact public hostname. Slice 8 adds workspace allowance, scoped project byte/inode usage/limits and enforcement health. Existing loop-image registrations retain their own mount checks until explicitly transitioned. Hide host filesystem paths from the ordinary overview; show sanitized operational identifiers in details.
- **Recovery:** distinct last local archive, off-host read-back, restore drill and approved-binding reference verification. An existing file or recent upload is not “recoverable.” Show RPO policy and overdue/unknown status.
- **Operations:** chronological setup/access operations, actor, reason, result and safe correlation IDs. Expand to show checked steps; raw shell logs, emails from business data and secrets are never response content.

### Latency, failure and accessibility

All status queries and operations are asynchronous. Keep the shell/navigation responsive, announce results and retain input after validation errors. Poll an open active job at a bounded interval (for example two seconds with backoff); use slower visible-only overview refresh and stop polling hidden pages. Show observation times and retained stale data during connection loss. Missing readings never become green/zero.

Disable duplicate submissions while awaiting a result, but retain the original operation key. A lost response offers **Check operation**; do not silently create another job. Stale revisions offer **Review latest status** while preserving edits. Closing a setup draft offers **Save and close** / **Discard draft**; discard only before provisioning starts. Once provisioning starts, **Stop setup** requests a safe checkpoint and retains created resources in a disabled state. It does not remove a Unix account or filesystem.

Keyboard focus moves to the step heading/error summary; confirmations are labeled and keyboard operable; status changes use restrained live announcements. Do not rely on color alone. No business-record entry, cross-operator search or “sign in as operator” control belongs here.

## Backend boundaries and security

### Separate control plane

Add a host-administration application with its own composition root, loopback listener, administrative store and session boundary. It can share a wheel/release with EPM but is a separate process and route inventory. Normal hosted/local EPM processes do not register these routes or inherit its credentials.

The unprivileged Admin HTTP process submits typed commands to a narrow local privileged broker over a root-controlled Unix socket. Authenticate the socket peer and bind each request to a validated Admin session/operation. The broker accepts fixed operation kinds and inventory IDs; resolves all paths, users, ports, units and release artifacts itself; validates ownership/no symlinks; and invokes fixed argument vectors without shell evaluation. No generic `exec`, arbitrary unit/path/file upload, sudo password, SSH key or browser-supplied environment.

Provisioning/mount/systemd changes require privilege. Run workspace initialization, seed generation, validation and owning access commands as the target service user. Root-owned Cloudflare/recovery credentials are available only to narrowly scoped adapters. Never mount every business workspace into the Admin HTTP process or open their databases to build the overview. Existing host administration is already trusted with system access; this design confines the added browser boundary rather than claiming protection from a malicious host root.

Use source-owned application operations for enrollment/disable/revoke/rebind. Extend the current CLI/application seam to return typed results and bounded administrative status; do not have the console manipulate another module's SQL rows or scrape its human-readable CLI text. Persist an authorization audit outcome atomically with each access-state mutation in that instance's access store; the control-plane log records the orchestration and evidence references separately. Cross-store failures reconcile through the operation journal, not a claimed distributed transaction.

### Source-owned command guarantees

**Repository implementation (Slice 2):** [AccessCommand](../../../application/apps/server/app/modules/hosted_access/application/admin_commands.py) and [source commands](../../../application/apps/server/app/modules/hosted_access/infrastructure/source_commands.py) provide the typed command/status/receipt seam. The current greenfield access schema records administrative revisions, binding revisions/configuration digests, fences, immutable receipts and safe mutation audits. The private CLI retains its recovery role; the browser/broker path does not scrape its prose or inherit its emergency activation override. Onboarding recovery completion and coordinated renewal remain Slice 6; ordinary enable stays blocked without its trusted recovery/acceptance checker. See the [authority runbook](../operations/HOSTED_ADMIN_AUTHORITY.md) for focused proof and deployment qualification boundaries.

The source-owned command envelope must carry operation ID, semantic hash, expected binding revision, administrator authority reference, instance fence and exact enrollment reference. In one access-store transaction, validate the local fence, apply the mutation, append its safe audit and persist the original result. Matching retries return that result without incrementing generation twice. Changed inputs conflict. All grant-enabling operations reject stale fence/revision even if retained enrollment exists. Keep session generation, administrative revision and immutable binding revision distinct. Extend the current greenfield schema and retained validation; no compatibility migration project is implied.

The broker owns command admission and durable dispatch. Authenticate its Unix peer against the dedicated Admin process identity; do not trust a caller-supplied administrator name/session ID as proof. Validate action authorization against protected session/grant records and bind it to the admitted request. Treat the HTTP service as a trusted but narrowly privileged component and document that compromise of it affects its admitted authority; typed RPC is not independent proof of human approval. Qualification CLI commands use the same admission/receipts rather than a second unfenced mutation path.

### Admin authentication

Bootstrap credential: at least 256 random bits, hash-only storage, one use, five-minute expiry, issued through an allowlisted IAP/SSH administrator command. Admin session: opaque token in an HttpOnly, SameSite=Strict, host-only cookie; 30-minute idle/eight-hour absolute expiry with explicit reauthentication for authority-increasing or binding-changing actions; the containment exception is defined below. The forwarded HTTP endpoint is loopback-only: do not claim a Secure-cookie guarantee over plain HTTP. The accepted initial profile is HTTP over the private IAP forward with a dedicated loopback hostname; document its local-process threat and tunnel dependency. Local HTTPS is deferred and requires explicit certificate provisioning/trust/renewal design before adoption. Use a distinct cookie name and fixed launcher port/Host allowlist so it cannot be confused with an operator session. Cookies are not isolated by TCP port: a distinct name alone does not isolate another localhost application. Use the dedicated loopback hostname with host-only cookies and explicit resolution/Host/Origin checks; qualify the exact HTTP launcher profile. Never bind the forward to a LAN/wildcard address. A local process with the same host access remains within the documented threat boundary.

Require exact Host/Origin and session CSRF for unsafe requests, reject cross-site Fetch Metadata, deny CORS and arbitrary forwarded headers, and keep CSP/frame restrictions. Bootstrap credential exchange requires the same origin protections. Limit attempts and do not log request bodies/credentials. Revoking Admin access fences its jobs before further steps; IAP revocation alone must not be assumed to terminate an already established forward. No admin role is inferred from an operator cookie or email header.

### Reauthentication, reconnect and committed work

For an uncommitted authority-increasing or binding-changing action (approve identity, complete onboarding, enable, renew, rebind or qualification promotion), obtain a new one-use grant through the same IAP/SSH launcher. The console exchanges it at the reauthentication endpoint for a server-held, single-use authorization bound to the Admin identity/session, exact action/request hash and target revision, expiring in five minutes. Consuming it and admitting the durable operation are atomic. This avoids asking for a fresh grant again when an already admitted operation is merely being looked up after a lost response. A reauthentication response alone never submits the action: show the reviewed current action and require explicit confirmation.

**Availability improvement:** allow Disable access and Revoke all sessions with the existing valid Admin session, CSRF, reason, explicit confirmation and current authority, without requiring a fresh SSH grant. These reduce access and must not depend on an additional provider/SSH round trip. If the session is expired or the console is unavailable, the private recovery CLI remains the authenticated containment path. This exception grants no ability to enable, renew, rebind or promote. Resume of a grant-enabling job still requires fresh action authorization.

| Event | Committed job / administrator next step |
| --- | --- |
| IAP forward or browser connection lost | Already admitted bounded work continues to its next durable checkpoint or human gate. Restart the launcher/forward, obtain a new bootstrap grant if the session is unusable, then retrieve the original operation; no automatic mutation replay |
| Idle or absolute Admin session expiry | Session/CSRF expires; admitted work retains its original authorization while the administrator identity remains enabled. Pending human gates and new commands wait for a new session and, where required, action-bound reauthentication |
| Explicit console logout | Revoke that browser session, clear local credentials, and stop new UI commands. It does not cancel committed work; label this on logout and offer a separate safe-stop request before logout when desired |
| Administrator authority revoked | Increment the durable administrator authority generation, revoke sessions/grants and fence owned jobs from further consequential steps. An in-flight external effect is reconciled at the checkpoint; if it could grant access, use containment and keep the job paused. Only an authorized administrator can explicitly review/resume it |

Workers check current administrator authority generation as well as instance fencing before every consequential step; browser session expiry alone is not identity revocation. A committed approval may therefore finish after a network drop or ordinary logout, but a queued activation must not cross a recorded administrator-revocation fence. Do not automatically undo an already completed approval solely because its response was lost.

Keep acknowledged setup drafts and operation/action keys in the control-plane store under the administrator's stable identity, independent of session lifetime. Non-secret draft/operation IDs may be in canonical console routes. On authentication loss, preserve that safe return route; after sign-in, reload its saved draft or operation from the server. Unacknowledged input is visibly unsaved and may require re-entry; do not claim it was saved or persist sensitive form content in browser storage.

If an action response was lost before an operation ID arrived, use an authenticated exact lookup by the original idempotency key, or the administrator's bounded recent-operation list after browser restart. If found, show its original result/status. If not found, explicitly re-read the target revision and enrollment/evidence, obtain fresh action authorization as needed, and let the administrator confirm the original unchanged intent/key. If the reviewed request must change, abandon that uncommitted intent and create a new key after review. Neither sign-in nor returning to the page silently resubmits an approval. **Resume** after an administrator-authority fence requires new authorization and a current revision review; it does not reuse the revoked grant.

### Authoritative host inventory

Use a separate protected control-plane SQLite database outside all portable workspaces:

| Record | Essential content |
| --- | --- |
| Instance | Stable instance UUID/key, operator/workspace UUIDs, exact intended email, hostname, allocated port, installed release/profile/template IDs, lifecycle, revision, timestamps |
| Allocation | Unique hostname/port/user and storage backend identity; Slice 8 filesystem/directory/project IDs, quota/profile and aggregate host commitments; existing mount/image identities retained until controlled retirement; owning instance/operation and retirement status |
| Operation | UUID, stable administrator identity/authority generation, idempotency key, canonical request hash, expected revision, status, safe error/result, cancellation flag, timestamps |
| Step | Stable sequence/kind, desired spec hash, provider IDs, verified external effects, checkpoint and reconciliation evidence |
| Qualification | Release/resource-profile identity, test authorization and reservations, controlled identities, tested operator/device count, workload, measured latency/headroom/recovery results, evidence date and explicitly promoted ordinary ceiling |
| Recovery handoff/evidence | Instance/workspace identity, binding revision/configuration digest, protected verifier provenance, point/digest/restore/age results, acceptance reference, status and completion operation; no credentials |
| Observation | Bounded service/resource/recovery fact, source and checked-at time; disposable and explicitly stale when unavailable |
| Admin audit/session | Append-only safe operation events; separate hash-only expiring sessions/bootstrap grants, excluded from recoverable authority |

Business records remain in their original owning modules. Existing per-instance access stores remain authoritative for enrollment, generation, sessions and leases; the inventory's access status is observed, not a duplicate authority. Enforce unique active email, hostname, port, instance key and workspace identities. Use server-generated opaque instance keys; retain A/B as existing allocated keys and never derive C from a count or email.

Discovery is reconciliation, not automatic adoption. Register A/B by inspecting root-owned configuration, effective systemd commands, mount identities and access bindings, then administrator confirmation. A discrepancy or unmanaged `epm-hosted@*.service` blocks destructive cleanup and further conflicting allocations. Never overwrite a populated path to “repair” inventory.

### Reconciliation with private tools and unknown resources

**Repository Slice 1:** [release cleanup](../../../application/scripts/release_cleanup.py) and the [VM wizard](../../../application/scripts/epm-release-vm.sh) now consume checked registered allocations and enter the same private host-maintenance lock/journal. Fixed private commands support explicit discovery, adoption, result lookup, resume and reconciliation. Effective configurations, release/tool digests and mount/access identities are preserved without manufacturing old acceptance or verified business recovery. See the [tooling runbook and focused matrix](../operations/HOSTED_INSTANCE_TOOLING.md). The installed host must still be transitioned and qualified; a repository change does not establish that existing private writers use this boundary. All supported private workflows must use the broker admission and source receipts, acquiring the same host/instance maintenance reservation and publish operation/checkpoint outcomes. Include disabled units, drop-ins, fstab mounts/images, retained access stores, rollback references and externally managed tunnel resources in discovery. Never rely only on currently running processes to protect a release.

Provide a read-only **Inventory discrepancies** view with observed versus registered identity/configuration and exact remediation. Unknown resources reserve their observed names/ports/storage and block conflicting mutation; they are never adopted or deleted automatically. Private maintenance requires Begin maintenance / observed completion / explicit reconciliation before ordinary grants resume. A stopped instance may retain a release needed for rollback. If legacy/private tooling cannot yet honor this contract, keep new-instance creation disabled until the tooling slice is complete.

Root break-glass containment/recovery remains available privately. Record its use where possible, detect resulting discrepancies, and require reconciliation before grant-enabling commands resume. The system does not claim to prevent intentional root bypass.

### Durable operations and failure handling

Provisioning is a resumable saga because filesystem, SQLite, systemd and Cloudflare cannot commit atomically. Suggested states:

`draft → provisioning → awaiting_external_setup / waiting_for_sign_in → awaiting_approval → identity_approved_recovery_pending → active`

Separate access flags and service observations from lifecycle; also represent `failed_step`, `disabled`, `expired` and `retired`. A healthy process is not evidence of active access or successful onboarding.

Reserve allocations and write the operation in one control-plane transaction. One mutating operation per instance; serialize host allocations, mount changes, route/config publication and capacity reservations. Never hold a database transaction open over provider/network calls. Read-only status and urgent disable remain available while a long job runs; disable fences queued activation and wins over subsequent resume. Use a per-instance authority generation checked before every grant-enabling step.

Urgent disable is a priority fence, not an ordinary mutation waiting behind the provisioning queue. Commit the disable intent/fence first; all current and future grant steps must validate it in their owning access-store operation. Reconcile an in-flight external effect and contain it before acknowledging completed disable. Enforce bounded worker claim leases and recovery of abandoned claims; workers must recheck fencing after a slow call, not only before it. Cancel never converts a failed creation into a successful active instance.

Tunnel/configuration publication affects the shared host. Use one host publication lock, read the latest full configuration, preserve unrelated routes, validate the candidate, publish atomically and verify A/B health as well as the target. Do not overwrite with a stale whole-file snapshot or roll back someone else's later change. A provider timeout is Unknown outcome, not Failed without effect. Persist exact resource IDs/spec digests and inspect before retry; ambiguous ownership requires private remediation.

Each step records intent before its external effect, then verifies the effect and checkpoints. After a crash between effect and checkpoint, inspect actual ownership/spec/provider IDs before retrying. Identical operation key/request returns the original result; changed payload with the same key is 409. Changed desired settings need a new reviewed request/revision. A lost browser response is resolved by operation lookup. Do not assume Cloudflare provides the same idempotency semantics: adapters reconcile exact tagged resource identity and refuse ambiguous duplicates.

Failure leaves the new instance access-fenced, preserves resources and shows the failed step plus **Resume** or private remediation. Do not delete resources automatically. Compensation removes only a provably operation-owned, unaccepted resource after explicit administrator confirmation; it never touches A/B. Do not auto-reactivate after cancellation, restore, renewal failure or a later disable.

## Proposed API contracts

These belong only to the private Admin service. Business `/api/hosted/*` and operator APIs retain their existing authorization. Use generated OpenAPI types and the shared problem envelope/status mapping; validation is 422, oversized content 413, missing resources 404, stale/conflicting requests 409, absent/denied authority 401/403, rate limits 429 (with Retry-After where meaningful), unmet qualification/capacity prerequisites 409 with a stable blocker code and remediation, unavailable dependencies 503. Pending jobs return 202; lookup returns 200 with operation state.

| Contract | Purpose |
| --- | --- |
| `POST /admin-api/session` | Exchange single-use SSH bootstrap grant for Admin session/CSRF |
| `GET /admin-api/session`, `DELETE /admin-api/session` | Current authority and logout |
| `POST /admin-api/session/reauthenticate` | Exchange a fresh SSH grant for single-use action authorization bound to intent hash/target revision; does not execute the action |
| `GET /admin-api/overview` | Independent capacity, attention and source availability summaries |
| `GET /admin-api/instances?cursor=…&state=…` | Bounded directory, total and observed status; no workspace reads |
| `GET /admin-api/instances/{id}` | Revision, safe configuration, enrollment summary, service/recovery observations |
| `POST /admin-api/setup-drafts`, `PATCH/DELETE /admin-api/setup-drafts/{id}` | Versioned unsent setup only; cannot discard started provisioning |
| `POST /admin-api/instances` | Confirmed setup snapshot/revision plus idempotency key → operation and instance IDs |
| `POST /admin-api/instances/{id}/actions` | Typed approve-identity/disable/enable/revoke/renew/complete-onboarding intent, expected revision, reason and idempotency key; identity approval includes exact enrollment reference and leaves access fenced; completion requires fresh action authorization, verified recovery and acceptance IDs and enables access through its owning receipt |
| `GET /admin-api/instances/{id}/recovery-handoff` | Persistent private-step instructions, handoff ID and required/current evidence status |
| `POST /admin-api/instances/{id}/recovery-handoff/check` | Verify broker-registered evidence for the handoff and expected current revision; never accept browser-supplied success claims |
| `GET /admin-api/operations/{id}` | Durable status, safe ordered steps and original result |
| `GET /admin-api/operations/by-key/{key}` | Authenticated exact lookup of the administrator's original request after a lost response; static route precedes the ID route |
| `POST /admin-api/operations/{id}/resume` | Resume the same validated intent; no settings mutation |
| `POST /admin-api/operations/{id}/cancel` | Durable safe-stop request; no implied resource deletion |

No request accepts arbitrary host paths, Unix usernames, shell commands, Access audience overrides or service-unit names. Read/write profiles expand only to existing valid capabilities. Bound strings, bodies, page sizes and retained operations/drafts; never silently prune failed or live jobs needed for reconciliation. Scope read query budgets to the control-plane store: a directory page uses a fixed number of bounded queries, not one per workspace or provider call. A background inventory sweep records observations; opening the overview must not fan out to all business services or Cloudflare.

## Capacity and additional-instance admission

The current 4 GiB VM may accommodate three lightly used portfolios; the observation above cannot justify unlimited operators. Keep the initial qualified maximum at two until the extension passes acceptance. Capacity evaluation includes a running Admin service/broker, all reserved instances, OS/tunnel overhead, backup staging, preserved resets/releases and off-host recovery costs.

Do not copy A/B's 1,500 MiB hard limit blindly to C: three such limits alone total 4,500 MiB. Qualify a smaller per-instance profile against realistic peak memory, or explicitly approve a larger VM. A profile must reserve at least 25% host memory for OS/host services/headroom and accommodate aggregate enforceable service limits inside the remaining envelope, including Admin processes. CPU remains a shared sustained budget; measure concurrent loads and throttling rather than summing CPUQuota percentages. No automatic billing change or cap reduction. A/B alone have combined 3,000 MiB hard caps against approximately 2,931 MiB under the new 75% envelope. Preserve their earlier qualified operation as a baseline exception; it does not authorize expansion or implicit Admin deployment. Qualify the combined Admin/application footprint before rollout and all running instances against the new envelope before expansion/profile promotion.

For the delivered backend, reserve fully allocated per-instance images plus measured initialization and recovery/reset staging. Under Slice 8, replace image preallocation with explicit commitments for all project hard limits, scratch/control budgets and shared overhead; account separately for occupied bytes and outstanding growth so neither is counted twice. Quotas alone do not reserve disk. Deny admission if free disk after outstanding commitments is below the greater of 20% filesystem capacity or the largest supported recovery job's measured requirement. Count retained disabled portfolios, retained old images, inodes and existing reservations. Use measured archive expansion/staging bounds; the usable workspace allowance is not the full disk cost of one operator.

Record a qualified operator/device ceiling for a specific release and resource profile. For C, test three operators with two active browsers each and staggered reports/uploads/backups; preserve existing latency gates and at least 25% memory headroom without OOM/restarts. The number of Access seats is a separate check, not a server-capacity setting. Unknown provider quota/capacity blocks invitation/activation while allowing draft setup.

Before general C invitations, qualify automatic tunnel startup and the resulting mount → instance → ingress recovery behavior. Until separately approved and tested on the host, retain the current manual-start policy and show Public access unavailable / administrator start required after reboot. Design approval is not authorization to enable the live unit. More operators amplify the same VM failure domain.

### Private path from a ceiling of two to three

Qualification is a separate private, broker-enforced operation available through the IAP administrator CLI; the console's **Qualification plan** displays its status and evidence. It is not a checkbox override on **Add operator** and cannot invite an ordinary third operator. Implement the following procedure before the ordinary capacity blocker ships:

1. **Record a bounded test plan.** Select the installed candidate release/profile, target of three simultaneous test instances/six browsers, controlled tester emails, exact protected test hostnames, storage/recovery reservations, time-limited test window, maintenance/rollback plan and evidence directory ID. Use distinct verified identities controlled by consenting testers; do not impersonate existing operators. The broker issues a durable qualification ID and permits only those exact test allocations. The ordinary ceiling stays two. The exception bypasses only the prior measured count, never physical capacity, storage, identity, resource ownership or access checks.
2. **Make physical capacity available.** Three candidate service limits plus host/Admin reservation must fit the selected VM before starting tests. If that requires smaller limits or a larger host, use an explicitly approved private profile/deployment change first. If A/B plus the three tests cannot fit, arrange a disclosed maintenance window, fence/drain/stop A/B, create verified recovery points and preserve their configurations/data/allocations. Test instances replace their running load temporarily; they do not overwrite their workspaces. Count all retained disk and recovery commitments. If the budget still cannot fit, stop the plan; neither the UI nor CLI may overcommit it.
3. **Run three isolated test instances on this host.** Provision fresh synthetic workspaces and test-specific Access applications/policies/routes through the same typed provisioning steps, bound to the qualification ID and controlled identities. No ordinary invitation copy/activation is available for these instances; private tester instructions permit only the named test participants. Existing normal workspaces remain inaccessible to the testers. Isolated test roots used in unit tests are prerequisites, not a substitute for these Linux/Cloudflare tests.
4. **Collect host evidence.** Exercise all three with six browsers and the specified concurrent/background workload; verify isolation, latency/headroom, independent off-host recovery/restore, expiry/revocation, shared-filesystem/enforcement failure and the chosen real reboot/tunnel-start policy. Include Slice 8 project/sandbox, byte/inode, allowance and scratch boundaries at the selected tiers. Register immutable digests and observed outcomes under the qualification ID through trusted private tooling. Record the exact VM, release/storage profile and test workload; failures remain failures and leave the ordinary ceiling unchanged. A planned VM reboot requires the maintenance window even if A/B could otherwise stay running.
5. **Retire tests and restore ordinary service.** Disable/revoke all test identities, stop test writers and remove their ingress before restoring A/B from preserved bindings/configurations (normally no data restore is necessary). Require fresh eligible sign-in after fencing, verify A/B access and data, and record preserved test evidence and any retained storage. Release test reservations only after their effects are verified; no automatic deletion or test-to-customer reassignment. If recovery to A/B fails, leave the test failed/unfinished and do not promote capacity.
6. **Explicitly promote the ceiling.** If the tested release/profile differs from restored A/B, explicitly roll it out to A/B through the private deployment procedure, recheck their data/access and resource limits, and record rollback evidence before promotion. A reauthenticated administrator uses the private qualification command to review the complete evidence, A/B restoration/rollout, current matching host/release/profile and absence of conflicting reservations. Commit an audited promotion to three under an expected inventory revision and idempotency key. A typed administrator declaration without the registered evidence cannot promote. The console now shows **3 qualified**, and ordinary **Add operator** can provision a fresh C using normal admission, enrollment, recovery and acceptance. Never convert a test subject/workspace into C by renaming it.

The profile used by the ordinary running instances must match the tested profile; applying it to A/B is an explicit qualified rollout, not an implicit consequence of promotion. Changes to host size, release/profile or tested workload bounds invalidate applicability until reviewed/requalified. A/B retain their original qualified configuration if the proposed profile fails. The CLI and broker own test-plan creation/resume/abort/evidence/promotion with the same durable-operation and reauthentication rules; their concrete command syntax is an implementation deliverable, not a claim that the commands exist today. UI status must link to the installed command's documented usage and never recommend a manual database edit.

## Resolved review decisions — October 27, 2026

All eight review recommendations are accepted and incorporated into the workflows and contracts above:

1. Preserve existing A/B operation as a capacity-policy baseline exception; expansion requires the new qualified envelope, with no silent cap reductions.
2. Approve identity while access remains fenced; verify recovery and explicitly complete onboarding before enabling business sessions.
3. Permit disable/revoke with valid Admin authority, CSRF, reason and confirmation; new access/binding authority still requires fresh authorization.
4. Route supported private maintenance through shared broker/fencing/receipts; retain documented root emergency recovery with mandatory reconciliation.
5. Warn about recovery age at 20 hours, overdue at 24; block new onboarding but do not automatically disable existing users. Restore drills are required at onboarding and after recovery-tool/format changes. A recurring drill interval remains an explicit operations-policy input before routine operations acceptance.
6. Qualify automatic tunnel startup before general C invitations; retain manual startup until that separate live change is approved and tested.
7. Permit explicit reasoned renewals without a cumulative pilot lifetime cap; each window is at most fourteen days, with visible renewal/retention history.
8. First release uses verified manual Cloudflare setup and a dedicated loopback HTTP hostname over IAP. Provider automation and local HTTPS require their own later qualification.

These decisions establish design scope, not deployment readiness or permission to change the live host.
